Chapter 10

Reasoning: teaching the graph to conclude

How a two-line rule turns "big spender" into a live definition that works across Aurora and Redshift, without adding a column anywhere.

It's Monday, and marketing wants one number: "How many big spenders do we have, per state?" There's no big_spender column and no large_order flag. The prices are in Redshift and the states are in Aurora, so no single SQL statement can join them. The old way is to query Redshift, paste 445 customer ids into an IN (…) list on Aurora, group by state, and repeat it next Monday, in the dashboard, and in the agent's prompt. By the end of this chapter you'll get that answer from one short SPARQL query over live rows, using a definition written exactly once, because Stardog will conclude facts nobody ever stored.

10.1Inference: facts you never stored

Every triple you've queried so far was asserted: a mapping or an INSERT DATA said it explicitly. Inference means deriving new triples from asserted ones plus the model. Stardog calls the machinery reasoning, and per its docs it "does not materialize inferences; rather, reasoning is performed at query time." With reasoning on, Stardog finds everything the model implies, answers, and throws the derivation away. Four terms carry this chapter:

TermWhat it isWhy it existsTiny example
InferenceDeriving a triple nobody asserted.So facts that follow from your data don't need storing or syncing.From customer:225 a :Big_Spender and :Big_Spender rdfs:subClassOf :Customer, infer customer:225 a :Customer.
RuleAn IF { pattern } THEN { triples } stored in the model.Subclass axioms can't test values ("price over 250"); rules can.IF { ?o a :Order ; :purchasePrice ?p . FILTER(?p > 250) } THEN { ?o a :Large_Order }
Derived classA class whose members come only from rules or axioms, never from data.To name a business concept once, in the model.No mapping says a :Large_Order. The rule decides, fresh on every query.
Reasoning level (Stardog: reasoning type)Which family of conclusions is allowed.More expressive logic costs more, so you choose.RDFS does subclasses but ignores rules. SL does both.

A derived class is closest to a view: CREATE VIEW large_order AS SELECT id FROM purchase WHERE price > 250. The analogy stretches: a view lives in one database and must be named to be used, while a rule applies across every source and fires implicitly, chaining on its own. Like a non-materialized view, it has no refresh step and no index.

A rule is a derived getter: computed on read from other fields, never stored.

Stardog rule

IF {
  ?sub a :Customer .
  ?o :purchasedBy ?sub .
  ?o a :Large_Order .
}
THEN {
  ?sub a :Big_Spender .
}

Java

// no boolean bigSpender field anywhere
static final Predicate<Order> LARGE =
    o -> o.price().compareTo(new BigDecimal("250")) > 0;

boolean isBigSpender(Customer c) {
  return orders(c).stream().anyMatch(LARGE);
}

Where the analogy breaks: you call isBigSpender() by name, but a rule also changes answers to questions that never mention it (ask for :Customer and big spenders come in via subClassOf), and it runs over two databases the JVM never loaded.

10.2Reasoning levels and schemas, in one page

Reasoning typeUnderstands
RDFSsubclasses, subproperties, rdfs:domain/rdfs:range
QL, RL, ELthree standard OWL 2 "profiles," subsets of OWL picked so reasoning stays fast (e.g. owl:inverseOf from Chapter 6)
SL (default)Stardog's combination of RDFS, QL, RL and EL, plus user-defined rules

kit-c360 uses SL, which matters because Stardog's troubleshooting guide says user rules "are only evaluated using the SL reasoning type." You won't change it.

The setting you will touch is reasoning.schemas from Chapter 6. A reasoning schema is a named set of graphs whose axioms and rules the reasoner uses. You have one, c360_schema, and you'll add a second. Per the docs, a query uses exactly one schema; Stardog doesn't merge them. So there are two dials per query: reasoning on or off, and which schema.

10.3Reading a real rule

A Stardog rule (Stardog Rule Syntax, or SRS) is a SPARQL pattern with a conclusion attached: "wherever IF matches, act as if the THEN triples exist." IF can hold the SPARQL you learned in Chapter 4 (triple patterns, FILTER, BIND, UNION, VALUES). The docs add three restrictions: every THEN variable must appear in IF; no variable may stand in the predicate position or as the class in rdf:type; and recursion is limited. Here is the kit's big-spender rule, copied exactly from c360_extended_rules.ttl:

IF {
  ?sub a stardog:ecomm:Customer .
  ?obj_0 stardog:ecomm:purchasedBy ?sub . ?obj_0 a stardog:ecomm:Large_Order .
}
THEN {
  ?sub rdf:type stardog:ecomm:Big_Spender .
}

In English: "if ?sub is a Customer, and some order purchased by ?sub is a Large_Order, then ?sub is a Big_Spender." Names like ?obj_0 are what Stardog Designer generates when you build a rule by drag-and-drop.

The prefix puzzle

Our mappings say :Customer; the rule says stardog:ecomm:Customer. If those were different classes, every rule would silently match nothing. The kit file declares @prefix stardog: <tag:stardog:api:>, and a prefixed name is the prefix IRI plus everything after the first colon (Chapter 3):

Written asExpands to
stardog:ecomm:Customertag:stardog:api: + ecomm:Customer = tag:stardog:api:ecomm:Customer
:Customer (our mappings, : = tag:stardog:api:ecomm:)tag:stardog:api:ecomm:Customer

Two spellings of one IRI (Turtle allows a colon inside the local part). Two traps. First, the same file also declares an unused @prefix : <http://api.stardog.com/>; write :Big_Spender under that header and you mint a class nobody uses. Second, the rule text is a string (rule:content """…"""), so Stardog resolves its prefixes with the database's namespaces, not the file's @prefix lines. stardog:, rdf: and xsd: are known out of the box.

10.4The kit's five rules, and one firing

c360_extended_model.ttl is the Chapter 6 ontology plus five derived classes, each a subclass of Order or Customer. c360_extended_rules.ttl holds one rule per class. The two files add up to 197 triples (172 + 25). The last column is my answer key, computed with read-only SQL against the rows you'll query.

Two rules chain: big spenders needs large purchases, and 2022 orderers needs 2022 orders. You never say what order to run them in. Press Play to watch a chain fire on three real orders:

How a rule is stored. A rule is data too: a blank node a rule:SPARQLRule (rule: = tag:stardog:api:rule:) with an rdfs:label and the text in rule:content, which is what the reasoner reads. Two more triples, <tag:stardog:designer:rule:content> and <tag:stardog:designer:rule:data>, are Designer's copy of the text and a blob it uses to redraw the rule. Five triples times five rules gives the file's 25.

Where the threshold lives: FILTER(?dat_0 > "250"^^xsd:decimal) on purchasePrice, which our Redshift mapping takes from the price column: the unit price (Chapter 9 multiplied it by quantity). So a "large order" is a purchase line with a unit price over $250, not a basket over $250.

Read the definition, not the name. Under this rule 445 of our 500 customers (89%) are "big spenders," because one item over $250 is enough. That's a business choice someone made in Designer, not a Stardog bug. The upside is that the definition is one visible line: change 250 to 5000 and every query, dashboard and agent that says "big spender" changes with it, instead of forty SQL files.

10.5Where reasoning runs: before the SQL is written

The big-spender rule needs Aurora ("?sub is a Customer") and Redshift ("an order over $250 purchased by ?sub"). The rule doesn't know that. It's written against the model, and the join works because both mappings mint the same customer IRI (Chapter 9's IRI trick).

The key point is when the rules run: inside Stardog's query planner, before the SPARQL-to-SQL rewrite. They aren't a batch job over copied data, and they aren't installed in Aurora or Redshift. The planner expands them into extra query patterns, and only then is the query split, turned into SQL, and sent to the live databases, so the rule logic always sees current rows. The docs support this picture (no materialization, and reasoning.rewriting "allows one to choose how query patterns are rewritten for reasoning") but don't publish the planner's internals, so treat these steps as a mental model rather than a spec:

  1. Expand. ?c a :Big_Spender becomes the big-spenders rule's IF pattern. That pattern mentions :Large_Order, which becomes the large-purchases pattern, including its FILTER.
  2. Rewrite to SQL. Now it's plain triple patterns, exactly what Chapter 9 federated. The Redshift part becomes something like … FROM c360.purchase WHERE price > 250, and the Aurora part becomes a select on customer joined to address.
  3. Join on the IRI inside Stardog, then GROUP BY state.

Reasoning is like composing a JPA Specification: predicates are combined first, and SQL is generated only when the query executes.

What the planner does

?c a :Big_Spender
  ↓ expand rule "big spenders"
?c a :Customer . ?o :purchasedBy ?c .
?o a :Large_Order
  ↓ expand rule "large purchases"
?o :purchasePrice ?p . FILTER(?p > 250)
  ↓ only now: SPARQL → SQL

Java

Specification<Order> large =
    (r, q, cb) -> cb.gt(r.get("price"), 250);
Specification<Order> spec =
    large.and(byCustomerState("WI"));

// nothing has hit the database yet
repo.findAll(spec);   // SQL generated here

Where the analogy breaks: you compose Specifications yourself; the reasoner composes them from the model whenever a query mentions a derived class, and may split the result across two engines.

reasoning.virtual.graph.enabled (default and here true) is what lets reasoning reach virtual graphs. Reasoning queries may send more SQL than plain ones, so don't loop them against a 1 RPU-hour daily cap.

10.6The Studio switches, and why the answer changes

Reasoning is off by default, per query: --reasoning on the CLI, reasoning=true over HTTP, and a Reasoning toggle in Studio's query toolbar. When a database has named schemas, Studio also lets you pick the schema (its release notes list "Support specifying a particular schema when querying"); in current versions the picker sits by the toggle. If yours looks different, tell Claude what you see.

The schema choice decides everything. Flip the toggle without picking one and you get the schema called default, which here is the special graph tag:stardog:api:context:schema, and it's empty: no rules, no big spenders. Pick c360_extended_rules. It's self-contained, because the extended model repeats the whole Chapter 6 ontology.

This is the open world (Chapter 5) at work. With reasoning off, no asserted ?c rdf:type :Big_Spender triples exist, so you get zero rows, not an error. With reasoning on, the identical text returns 42 rows. Only Stardog's permission to conclude changed.

Reasoning faithfully applies whatever axioms you write, bugs included. A real bug from the kit (Chapter 6 flagged it): schema.ttl says :rewardsAccountUsed owl:inverseOf :hasRewards, but rewardsAccountUsed goes Order → RewardsAccount and hasRewards goes Customer → RewardsAccount. Both point at the account, so they can't be inverses. (Its second axiom, :hasRewards owl:inverseOf :rewardsAccount, names a property declared nowhere else.) Under the c360_schema schema with reasoning on, each of the 1,560 purchases that used a rewards account produces a nonsense triple <rewards account> :hasRewards <order>.

How you'd spot it: count a property with reasoning off, then on; unexpected growth, or subjects of the wrong class, is the tell (step 9 below). How you'd fix it: delete the axiom, or replace it with a real inverse such as :usedInOrder owl:inverseOf :rewardsAccountUsed. This chapter's schema, c360_extended_rules, has no owl:inverseOf at all, one more reason the schema picker matters.

This is the blog's section "Reasoning over the graph." It defines Big_Spender as "a customer who has placed at least one order above a threshold," and says that with reasoning at query time "how many big spenders by state?" works "without precomputing or materializing those facts." The blog never prints the threshold; you just found it in the kit (purchasePrice > 250). Its one-line argument is worth keeping: encode business definitions once, "instead of re-implementing them in SQL queries, dashboards and prompts."

10.7Build step 5: load the rules, flip the switch

Before you start: aurora_c360_safe and redshift_c360 exist (Chapters 8 and 9), and reasoning.schemas holds c360_schema=…. If Aurora is asleep, the first query can take 15 to 20 seconds.

1. Load both kit files into one named graph. Databases → kit-c360 → Load Data. Download c360_extended_model.ttl and c360_extended_rules.ttl from Stardog's public GitHub repository (https://github.com/stardog-union/knowledge-kits/blob/main/examples/c360/models/c360_extended_model.ttl and https://github.com/stardog-union/knowledge-kits/blob/main/examples/c360/models/c360_extended_rules.ttl, Download raw file button), then browse to c360_extended_model.ttl. In the Load Data To dropdown (it starts at stardog:context:default), type this graph name into "Search or create…" and choose it:

urn:stardog:c360_extended_rules:1.0:model

Then load c360_extended_rules.ttl into the same graph.

2. Count (reasoning off). Expect 197. If you get 172 or 25, one file is missing.

SELECT (COUNT(*) AS ?triples)
WHERE { GRAPH <urn:stardog:c360_extended_rules:1.0:model> { ?s ?p ?o } }

3. See the rules as data. Expect 5 rows.

PREFIX rule: <tag:stardog:api:rule:>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?label ?content
WHERE { GRAPH <urn:stardog:c360_extended_rules:1.0:model> {
  ?r a rule:SPARQLRule ; rdfs:label ?label ; rule:content ?content . } }
ORDER BY ?label

4. Register the schema. Databases → kit-c360 → Properties, find reasoning.schemas, keep c360_schema=…, and add this value (the docs say it can be changed while the database is online):

c360_extended_rules=urn:stardog:c360_extended_rules:1.0:model

Save. The Models tab should now list both schemas.

5. Ask with reasoning OFF. Expect no rows.

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?state (COUNT(DISTINCT ?c) AS ?bigSpenders)
FROM <virtual://aurora_c360_safe>
FROM <virtual://redshift_c360>
WHERE {
  ?c a :Big_Spender ;
     :address ?addr .
  ?addr :state ?state .
}
GROUP BY ?state
ORDER BY DESC(?bigSpenders) ?state

The two FROM lines merge both virtual graphs into the query's default graph, so a rule can join across them.

6. Same text, reasoning ON, schema c360_extended_rules. You should see approximately this: 42 rows, 445 big spenders in total, starting

9. (Optional) Catch the inverseOf bug. Run this with reasoning OFF, then ON with schema c360_schema:

PREFIX : <tag:stardog:api:ecomm:>
SELECT (COUNT(*) AS ?n)
FROM <virtual://aurora_c360_safe>
FROM <virtual://redshift_c360>
WHERE { ?x :hasRewards ?y }

Expect about 500 with reasoning off (one per rewards_account row) and about 2,060 with it on (plus the 1,560 bogus account → order triples). Add ?x a :RewardsAccount . to the WHERE and the reasoning-on count is still about 1,560, though no rewards account should "have rewards." To fix the model, this removes the bad axiom (<urn:stardog:training-c360:1.0:model> goes from 161 to 160 triples). Nothing later depends on it.

PREFIX :    <tag:stardog:api:ecomm:>
PREFIX owl: <http://www.w3.org/2002/07/owl#>
DELETE DATA {
  GRAPH <urn:stardog:training-c360:1.0:model> { :rewardsAccountUsed owl:inverseOf :hasRewards }
}

Nothing to clean up. This is part of the real build.

  • Zero rows with reasoning ON? Nine times out of ten the query ran under the empty default schema. Check the schema picker.
  • Missing a FROM? Without the Aurora graph, ?c a :Customer never matches, so there are no big spenders. :Large_Order alone needs only Redshift.
  • Checked both and still nothing? Stop and send Claude the query and what Studio shows.

10.8When to reach for reasoning

Use it when a definition is shared and derivable: one definition, always fresh, applied across warehouses. Your Chapter 14 agent can then write ?c a :Big_Spender instead of re-deriving the threshold and the join. Skip it when you need a stored answer (an audit snapshot), heavy aggregation on every query, or bad data rejected. Reasoning only adds conclusions; saying "no" is the next chapter's job.

Check yourself

After the reasoning query, where is the triple "customer:225 a :Big_Spender" stored?

Nowhere. Stardog reasons at query time and doesn't materialize inferences. Turn reasoning off and the triple is gone.

Why is stardog:ecomm:Customer the same class as our :Customer?

stardog: = tag:stardog:api:, so the name expands to tag:stardog:api:ecomm:Customer, exactly what :Customer expands to when : = tag:stardog:api:ecomm:.

Reasoning is ON and the big-spender query returns nothing. Two likely causes?

The query ran under the empty default schema instead of c360_extended_rules (only one schema per query), or the Aurora virtual graph wasn't in the dataset, so ?c a :Customer never matched.

Do the rules run in Aurora and Redshift?

No. Stardog's planner expands the rules into extra query patterns first; only then is the query rewritten to SQL. The rule logic reaches the databases only as ordinary SQL (for example WHERE price > 250) over live rows.

What exactly makes a Large_Order here, and what does that imply?

purchasePrice > "250"^^xsd:decimal on the unit price. One pricey item is enough, so 1,103 orders and 445 of 500 customers qualify. It's generous, but it's defined in one place and easy to change.

Chapter recap

  • Inference derives triples from data plus model. Stardog does it at query time and stores nothing.
  • A rule is IF { pattern } THEN { triples }, stored as a rule:SPARQLRule. A derived class gets its members only from rules. The reasoning level must be SL (the default) for rules to fire.
  • The kit's five rules: Large_Order (price > 250), Big_Spender, 2022_Order, 2022_Orderer, Sports_Category_Shopper. Two of them chain.
  • stardog:ecomm:X = tag:stardog:api:ecomm:X = our :X.
  • Rules are expanded in Stardog's planner before SPARQL becomes SQL, so they always run over live rows.
  • Reasoning and the schema are chosen per query, and only one schema is used per query. Pick c360_extended_rules.
  • Reasoning applies bad axioms too (the kit's :rewardsAccountUsed owl:inverseOf :hasRewards). Compare counts with reasoning off and on.
  • Build step 5 is done: 197 triples loaded, a second schema registered, and "big spenders per state" going from 0 rows to 42 (445 customers).
