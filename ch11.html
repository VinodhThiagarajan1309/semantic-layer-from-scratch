Chapter 11

SHACL: when you do want rules to reject data

The closed-world checks a database person expects (NOT NULL, CHECK, foreign keys), written for a graph, run on demand, and reported, not enforced.

Try an experiment in your head. You INSERT a customer into Postgres with two email addresses, one of them "not-an-email", and an address id that doesn't exist. Postgres won't have it: a single email column can't hold two values, a CHECK rejects the malformed one, and the foreign key rejects the unknown address. Insert the same customer into Stardog as triples and it says "OK," then and later, reasoning or not. Which brings us to your question: what exactly does SHACL mean, and why do people use it? SHACL stands for Shapes Constraint Language, a W3C standard (a Recommendation since July 2017) for writing down what acceptable data looks like and checking real data against it. RDFS and OWL are designed never to reject anything. SHACL is the part of the RDF world that says "no, that's wrong," and tells you which node, which property and which rule.

11.1Why the ontology never said no

Two ideas from earlier chapters explain it. The open-world assumption (Chapter 5): a missing fact is unknown, not false, so a customer with no :email triple is not an error, where a closed-world database would reject the NULL. Axioms infer rather than reject (Chapter 6): if the model said :address rdfs:range :Address and an :address pointed at a product, RDFS would infer the product is an Address, which is why the kit uses the documentation-only so:rangeIncludes. Neither ever checks anything.

A tiny example of the gap. These two triples are fine to OWL:

<urn:stardog:demos:c360:customer:9999> :email "bad.customer@example.com" , "not-an-email" .

Two emails? A customer can have several. A malformed one? OWL only sees a string. If you come from Postgres, you want email varchar NOT NULL UNIQUE CHECK (email ~ '@'). SHACL is how you say that about a graph.

Two jobs, two tools. The ontology (RDFS/OWL) describes meaning: what a Customer is and what can be concluded. SHACL describes acceptable data: what a customer record must look like to pass inspection. Mature knowledge graphs have both.

11.2SHACL's vocabulary, broken down

SHACL is itself written in RDF (Turtle), using the namespace sh: = http://www.w3.org/ns/shacl#.

TermWhat it isWhy it existsTiny example
ShapeA named set of conditions that some nodes must meet.A reusable spec for a kind of record, like a table's constraints.:CustomerShape a sh:NodeShape

The smallest complete shape, "every Customer must have an email":

:EmailRequired a sh:NodeShape ;
  sh:targetClass :Customer ;
  sh:property [ sh:path :email ; sh:minCount 1 ] .

Against the data from Section 11.1, customer:9999 passes (it has at least one email). Add sh:maxCount 1 and it fails with "more than 1 value." Add sh:pattern "^[^@ ]+@[^@ ]+[.][^@ ]+$" and "not-an-email" fails too. That's the entire idea; the rest is detail.

11.3SHACL for a database person

The translation table to keep open:

You'd write in SQLSHACL constraintNotes
email NOT NULLsh:minCount 1"At least one value via this path."

A shape is Jakarta Bean Validation for graph data, almost one for one.

SHACL

:CustomerShape a sh:NodeShape ;
  sh:targetClass :Customer ;
  sh:property [ sh:path :email ;
    sh:minCount 1 ; sh:maxCount 1 ;
    sh:pattern "^[^@ ]+@[^@ ]+[.][^@ ]+$" ] ;
  sh:property [ sh:path :address ;
    sh:minCount 1 ; sh:class :Address ] .

Java

class Customer {
  // RDF is multi-valued, so model it as a list
  @NotEmpty @Size(max = 1)                    // min/maxCount
  List<@Pattern(regexp = "^[^@ ]+@[^@ ]+[.][^@ ]+$")
       String> emails;                        // sh:pattern

  @NotEmpty
  List<@Valid Address> addresses;             // ~ sh:class
}

Where the analogy breaks: annotations live on the class, and the compiler guarantees the element type. A shape sits outside the data, in its own graph, checks things Java gets for free (is the value really an Address?), and can be swapped without touching the data.

The biggest difference is when the check happens. A SQL constraint runs on every INSERT and blocks the bad row. SHACL, as normally used, is a report you run on demand, closer to a dbt test or a Great Expectations suite: the data is already there, and SHACL tells you what's wrong with it.

Stardog does offer a SQL-like guard mode, turned on with the database option icv.enabled (the docs show taking the database offline to set it), in which Stardog will "fail transactions that violate constraints." That only applies to data written into Stardog. Virtual graphs are never written through Stardog, so for us reports are the whole story. We won't turn guard mode on.

11.4The CustomerShape, line by line

The exercise's shape: every Customer has exactly one well-formed email and at least one address that is an Address:

:CustomerShape a sh:NodeShape ;
  sh:targetClass :Customer ;
  sh:property [
    sh:path :email ;
    sh:minCount 1 ;
    sh:maxCount 1 ;
    sh:datatype xsd:string ;
    sh:pattern "^[^@ ]+@[^@ ]+[.][^@ ]+$" ;
    sh:message "A customer needs exactly one well-formed email."
  ] ;
  sh:property [
    sh:path :address ;
    sh:minCount 1 ;
    sh:class :Address ;
    sh:message "A customer's address must be an Address."
  ] .

Top to bottom: a node shape that targets every :Customer (in Stardog including subclass instances, because shacl.targetClass.simple is false). Each sh:property [ … ] is a property shape, an unnamed (blank) node holding the checks for one path. minCount 1 ; maxCount 1 means exactly one value: NOT NULL plus single-valued. A plain "…" literal is an xsd:string, so sh:datatype passes for normal text. The regex uses [.] instead of \. to avoid escaping inside Turtle strings. sh:class :Address requires the value to have rdf:type :Address in the data being validated: the foreign-key check. sh:message is optional text copied into each result.

11.5Running validation in Stardog 12

Stardog calls its SHACL engine ICV (Integrity Constraint Validation), a name you'll see in options, the CLI and the HTTP API. Four ways to run it, all read-only for your data:

WhereHowReturns
Studio / any SPARQL clientThe VALIDATE query form (a Stardog SPARQL extension since Stardog 9)A validation report graph
Studio / SPARQLSERVICE icv:validate { … } inside a SELECTA table, one row per violation
CLIstardog icv report, stardog icv validateReport / pass-fail
HTTPthe database's icv/validate endpoint (icv/{tx}/validate inside a transaction), which the CLI and pystardog's report() call.As above

The VALIDATE grammar from the docs:

VALIDATE (ALL | [<IRI>+] [GRAPH <IRI>+])
  [USING SHAPES (<IRI>+ | GRAPH <IRI>+ | <QuadData>)]
  [LIMIT <int>] [LIMIT PER SHAPE <int>]

In words: say what data to check (all, specific nodes, or named graphs) and which shapes to use (shape IRIs, shapes stored in named graphs, or shapes inline in curly braces). LIMIT caps the number of results.

Where shapes live. Shapes are ordinary triples, and the docs' best practice is to store them in a named graph. The option shacl.shape.graphs says which graphs a plain VALIDATE ALL reads shapes from; on kit-c360 it's the default, tag:stardog:api:context:local, meaning all local graphs. So any shape left lying around in a local graph joins future VALIDATE ALL runs: clean up scratch shapes, and name the shapes graph explicitly with USING SHAPES GRAPH, as we will.

11.6Where SHACL fits in a federated setup

In our architecture the data isn't in Stardog; it's SQL rows seen through mappings. What could go wrong, and where?

  • Upstream data problems: a NULL email in Aurora, or a cid in Redshift with no matching customer. Fix these at the source, but a SHACL report shows them in the business vocabulary.
  • Mapping mistakes, where SHACL shines for us: a wrong IRI template (the address IRI doesn't match, so sh:class :Address fails for every customer), a missing cast (Chapter 9's xsd:float money becomes a sh:datatype xsd:decimal violation), a column mapped to the wrong property. The SQL looks fine, the triples are subtly wrong, and a shape catches them.

Can Stardog validate a virtual graph directly?

The main documentation page, Data Quality Constraints (docs.stardog.com/data-quality-constraints), doesn't mention virtual graphs. On the Stardog Community forum, Stardog staff have answered twice:

  • "SHACL validation for virtual graphs" (community.stardog.com/t/3238): Pavel Klinov explains that Stardog can't validate data before it enters a virtual graph (writes go straight to the source) and suggests keeping the shapes in Stardog and running stardog icv report --named-graph virtual://graph1 <db>. For big data he suggests a cache.
  • "SHACL validation on a Virtual graph" (community.stardog.com/t/4912): Paul Jackson gives the VALIDATE form, which needs a query hint: #pragma simple.target on, then VALIDATE GRAPH <virtual://graph_name> USING SHAPES { … } (lowercase virtual://). The user reported still getting sh:conforms true for shapes that should fail; the thread shows no resolution.

So it's supported in principle, not officially documented, and at least one user saw false "all clear" results. We'll do the documented thing: validate a small materialized sample in the scratch graph <urn:book:ch11>. An optional read-only stretch at the end tries the virtual graph with a built-in lie detector.

The AWS blog never mentions SHACL, validation or data quality. Its "meaning" layer is the ontology plus reasoning (Chapter 10), and its governance is named-graph security (Chapter 12). SHACL is what you'd add on the way to production: a scheduled VALIDATE with a handful of shapes, in the blog's start-small spirit.

11.7Try it: validate a sample, break it, fix it

Two scratch graphs, deleted at the end: <urn:book:ch11> for the data and <urn:book:ch11:shapes> for the shapes. The data uses real values for Jolynn (customer 1) and Carolyn (customer 225), plus a deliberately bad customer 9999, who doesn't exist in Aurora.

1. Insert the sample data. In Studio, database kit-c360, reasoning off:

PREFIX : <tag:stardog:api:ecomm:>
INSERT DATA {
  GRAPH <urn:book:ch11> {
    <urn:stardog:demos:c360:customer:1> a :Customer ;
        :name "Jolynn Bithany" ;
        :email "jbithany0@multiply.com" ;
        :address <urn:stardog:demos:c360:location:a7b8c114-78e0-441d-8ad2-560f92636841> .
    <urn:stardog:demos:c360:location:a7b8c114-78e0-441d-8ad2-560f92636841> a :Address ;
        :city "Austin" ; :state "Texas" .

    <urn:stardog:demos:c360:customer:225> a :Customer ;
        :name "Carolyn Inworth" ;
        :email "cinworth68@g.co" ;
        :address <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35> .
    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35> a :Address ;
        :city "Milwaukee" ; :state "Wisconsin" .

    <urn:stardog:demos:c360:customer:9999> a :Customer ;
        :name "Bad Customer" ;
        :email "bad.customer@example.com" , "not-an-email" ;
        :address <urn:stardog:demos:c360:location:does-not-exist> .
  }
}

Expect success and 17 triples (check with SELECT (COUNT(*) AS ?n) { GRAPH <urn:book:ch11> { ?s ?p ?o } }). Stardog accepted customer 9999 without complaint: the open world in action.

2. Store the shape.

PREFIX :    <tag:stardog:api:ecomm:>
PREFIX sh:  <http://www.w3.org/ns/shacl#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
INSERT DATA {
  GRAPH <urn:book:ch11:shapes> {
    :CustomerShape a sh:NodeShape ;
      sh:targetClass :Customer ;
      sh:property [
        sh:path :email ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:string ;
        sh:pattern "^[^@ ]+@[^@ ]+[.][^@ ]+$" ;
        sh:message "A customer needs exactly one well-formed email."
      ] ;
      sh:property [
        sh:path :address ;
        sh:minCount 1 ;
        sh:class :Address ;
        sh:message "A customer's address must be an Address."
      ] .
  }
}

A shape is just data, so it goes in with INSERT DATA.

3. Validate.

VALIDATE GRAPH <urn:book:ch11>
USING SHAPES GRAPH <urn:book:ch11:shapes>

Expect a report with sh:conforms false and three sh:result entries, all with focus node customer:9999:

  • sh:MaxCountConstraintComponent on path :email (two values).
  • sh:PatternConstraintComponent on path :email, value "not-an-email".
  • sh:ClassConstraintComponent on path :address, value …location:does-not-exist. That node has no a :Address triple.

Customers 1 and 225 produce nothing; silence means they pass. Studio shows the report as RDF; read it like the example in Section 11.8.

4. The same check as a table. Reports are easier to scan as rows:

PREFIX icv: <tag:stardog:api:icv:>
SELECT ?focusNode ?path ?component ?value ?message
WHERE {
  SERVICE icv:validate {
    [] icv:dataGraph   <urn:book:ch11> ;
       icv:shapesGraph <urn:book:ch11:shapes> ;
       icv:focusNode ?focusNode ;
       icv:resultPath ?path ;
       icv:sourceConstraintComponent ?component ;
       icv:value ?value ;
       icv:resultMessage ?message .
  }
}

Expect 3 rows, matching step 3. If you see fewer, delete the icv:value ?value ; line and rerun: a max-count result usually has no single offending value.

5. Fix the bad customer and re-validate.

PREFIX : <tag:stardog:api:ecomm:>
DELETE DATA {
  GRAPH <urn:book:ch11> {
    <urn:stardog:demos:c360:customer:9999> :email "not-an-email" .
  }
} ;
INSERT DATA {
  GRAPH <urn:book:ch11> {
    <urn:stardog:demos:c360:location:does-not-exist> a :Address ;
        :city "Nowhere" ; :state "Texas" .
  }
}

Run step 3 again. Expect [ a sh:ValidationReport ; sh:conforms true ]. One deletion cleared two violations (the second email was both the extra value and the malformed one), and the third cleared when the address became an Address.

6. Clean up (required).

DROP GRAPH <urn:book:ch11> ;
DROP GRAPH <urn:book:ch11:shapes>

Then confirm both are gone. This should return 0:

SELECT (COUNT(*) AS ?n)
WHERE { GRAPH ?g { ?s ?p ?o } FILTER(STRSTARTS(STR(?g), "urn:book:ch11")) }

Dropping the shapes graph matters: a forgotten :CustomerShape would quietly join every future VALIDATE ALL (Section 11.5).

11.8Reading a validation report

The kind of report step 3 returns, trimmed to one result:

[ a sh:ValidationReport ;
  sh:conforms false ;
  sh:result [
    a sh:ValidationResult ;
    sh:resultSeverity sh:Violation ;
    sh:sourceShape _:b0 ;                                  # the email property shape
    sh:sourceConstraintComponent sh:PatternConstraintComponent ;
    sh:focusNode <urn:stardog:demos:c360:customer:9999> ;
    sh:resultPath :email ;
    sh:value "not-an-email" ;
    sh:resultMessage "A customer needs exactly one well-formed email."
  ] ] .

Read it like a failed test: sh:focusNode is the bad row's primary key, sh:resultPath is the column, sh:value is the bad cell (when there is one), sh:sourceConstraintComponent says which check failed, and sh:resultSeverity says how much to care. sh:conforms is true only with zero results.

Same shape of call in both worlds: a collection of violations back, and empty means valid.

Stardog

VALIDATE GRAPH <urn:book:ch11>
USING SHAPES GRAPH <urn:book:ch11:shapes>

# → sh:conforms false
#   sh:result [ sh:focusNode customer:9999 ;
#               sh:resultPath :email ; … ]

Java

Set<ConstraintViolation<Customer>> v =
    validator.validate(customer);

// v.isEmpty()            ~ sh:conforms true
// cv.getRootBean()       ~ sh:focusNode
// cv.getPropertyPath()   ~ sh:resultPath
// cv.getInvalidValue()   ~ sh:value

Where the analogy breaks: validator.validate() checks one object in memory. VALIDATE scans every target node in a graph, and the report is RDF you can query or store.

Optional stretch (read-only): try the virtual graph, with a lie detector

Curious whether direct virtual-graph validation works on our server? VALIDATE only reads, so this is safe. The trick is a canary shape that must fail: aurora_c360_safe has no :ssn (Chapter 8), so "every customer has an ssn" must fail. If it reports conforms true, validation isn't really seeing the virtual data, so ignore any "all clear."

#pragma simple.target on
PREFIX :   <tag:stardog:api:ecomm:>
PREFIX sh: <http://www.w3.org/ns/shacl#>
VALIDATE GRAPH <virtual://aurora_c360_safe>
USING SHAPES {
  :CanaryShape a sh:NodeShape ;
    sh:targetClass :Customer ;
    sh:property [ sh:path :ssn ; sh:minCount 1 ] .
}
LIMIT 5

Expected if it works: conforms false with 5 results (capped by LIMIT 5; the true number is 500). Aurora may take about 20 seconds to wake. If that works, swap the canary for the two sh:property blocks of :CustomerShape and rerun. My read-only SQL check found all 500 real customers have exactly one well-formed email and an existing address row, so a working validator should report conforms true. If Studio rejects the syntax or the canary passes, tell Claude; that's useful information, not a failure on your part.

  • Empty report ≠ good data if the target matched nothing. Misspell the class in sh:targetClass and every node is skipped: conforms true. Canaries help everywhere.
  • sh:class checks the data graph you validate. A customer in one graph with its Address type in another fails sh:class if you validate only one graph.
  • Reasoning and SHACL are separate switches. Validation runs without reasoning (icv.reasoning.enabled is false on kit-c360), so derived classes like :Big_Spender aren't targets by default.

Check yourself

What does SHACL stand for, and why does it exist when we already have OWL?

Shapes Constraint Language, a W3C Recommendation from 2017. OWL and RDFS are open-world and infer rather than reject: a missing value is "unknown," and a range axiom adds a type instead of flagging an error. SHACL adds closed-world checks (required, single-valued, datatype, pattern, class) that produce a report of what's wrong.

Translate email varchar NOT NULL plus "one value per row" into SHACL.

sh:property [ sh:path :email ; sh:minCount 1 ; sh:maxCount 1 ; sh:datatype xsd:string ] inside a node shape that targets :Customer.

Our bad customer had two emails, one malformed. Why did deleting one triple clear two violations?

The extra value (maxCount) and the malformed value (pattern) were the same triple, :email "not-an-email".

Does a SHACL shape in Stardog stop a bad row from arriving through a virtual graph?

No. Writes go to Aurora and Redshift directly, never through Stardog, and guard mode (icv.enabled) only applies to transactions on data stored in Stardog. For virtual graphs, SHACL is a report you run.

Is validating a virtual graph directly supported? Cite your source.

Not in the main docs (Data Quality Constraints doesn't mention it). Stardog staff on the community forum describe stardog icv report --named-graph virtual://… and #pragma simple.target on + VALIDATE GRAPH <virtual://…>, but one user reported false conforms true. Possible, not officially documented; test it with a canary.

Why did the exercise drop the shapes graph, not just the data graph?

shacl.shape.graphs defaults to all local graphs, so leftover shapes would join future VALIDATE ALL runs.

Chapter recap

  • SHACL = Shapes Constraint Language (W3C, 2017): closed-world data checks for RDF, the counterpart to OWL's open-world meaning.
  • Vocabulary: node shape, property shape (sh:path), target, constraint component, focus node, validation report, severity.
  • SQL mapping: NOT NULL → minCount 1, scalar → maxCount 1, type → datatype, FK → class, CHECK → pattern/minExclusive/in.
  • In Stardog (ICV): VALIDATE GRAPH … USING SHAPES …, SERVICE icv:validate for a table, stardog icv report, HTTP icv/validate. Shapes live in named graphs (shacl.shape.graphs) or inline.
  • In a federation SHACL is a report, not a gate, and especially good at catching mapping mistakes. Direct virtual-graph validation is only described on the forum; test it with a canary.
  • You validated, broke, fixed and dropped <urn:book:ch11> and <urn:book:ch11:shapes>.
