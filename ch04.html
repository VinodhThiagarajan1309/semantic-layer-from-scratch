Chapter 4

SPARQL for people who know SQL

You already know how to ask a database a question. By the end of this chapter you will ask a graph the same questions, and watch the JOIN keyword quietly disappear into the arrows.

It is 4:55 on a Friday and someone from marketing leans over your desk: "Quick one. Which of our customers in Wisconsin spent the most?" You know the SQL: join purchase to customer on cid, customer to address on location, filter on the state, sum price times quantity, sort. You also know the catch: customers live in Aurora and purchases in Redshift, so "just join them" means an export, a staging table, or a pipeline. By Chapter 9 the graph will answer that question across both in one query. First you need the language the question is written in, and you already know most of it.

4.1What is SPARQL, and why does it exist?

SPARQL (pronounced "sparkle"; the letters stand for SPARQL Protocol and RDF Query Language) is the W3C standard query language for RDF graphs: to triples what SQL is to tables. SPARQL 1.1 (2013) added aggregates, subqueries and a write half called SPARQL Update. Every serious graph database, Stardog included, speaks it.

Why not just use SQL? Because SQL assumes tables with a fixed list of columns, and a graph has neither. You could store triples in a three-column table, triples(subject, predicate, object), but then every arrow you follow is another self-join, and SQL has no idea that <urn:…customer:225> is a global name, that "2013-04-18"^^xsd:date is a typed value, or that triples live in named graphs (Chapter 3). SPARQL builds those ideas in and makes "follow this arrow" the basic move.

The "Protocol" part defines how to send a query over HTTP and get JSON or CSV back. Every Stardog database is a SPARQL endpoint, a URL that accepts queries; that is how the agent in Chapter 14 will talk to our graph.

4.2A query is a picture with blanks

In Chapter 2 you learned that every fact is a triple: subject predicate object. Carolyn's name is customer:225 :name "Carolyn Inworth". A triple pattern is the same shape with some positions replaced by variables:

?customer  :name  ?name .

Read it aloud: "find anything that has a :name; call the thing ?customer and the name ?name." For every triple whose predicate is :name, the engine binds the variables. One match, one row.

A full query wraps patterns in WHERE { … } and lists the variables you want back:

PREFIX : <tag:stardog:api:ecomm:>

SELECT ?customer ?name
WHERE {
  ?customer :name ?name .
}

The PREFIX line is the shorthand from Chapter 3: :name expands to <tag:stardog:api:ecomm:name>. Every query in this book declares its prefixes, so each one runs on its own.

Picture the graph as one big List<Triple>. A one-pattern SELECT is a stream over it: the fixed parts become a filter, the variables the fields you map into a row.

SPARQL

SELECT ?customer ?name
WHERE {
  ?customer :name ?name .
}

Java 21

record Triple(String s, String p, Object o) {}
record Row(String customer, Object name) {}

List<Row> rows = graph.stream()          // List<Triple>
    .filter(t -> t.p().equals(":name"))  // the fixed part
    .map(t -> new Row(t.s(), t.o()))     // fill the blanks
    .toList();

Where the analogy breaks: the Java version says how (scan every triple, in this order). SPARQL only says what shape you want. Stardog keeps triples in several sorted indexes, and its planner chooses which to read and in what order. You describe the answer; the engine writes the loop.

Never rely on a database's built-in prefixes: a new Stardog database usually binds : to http://api.stardog.com/, not our tag:stardog:api:ecomm:. Forget the PREFIX : line and :name silently means an IRI no triple uses: the query runs and returns nothing.

4.3The shared variable is the join

Now put three patterns together and reuse variables:

?customer :name    ?name .
?customer :address ?addr .
?addr     :city    ?city .

Because ?customer appears in the first two patterns, both must match the same customer; because ?addr appears in the last two, the city must belong to that customer's address. That is the whole trick: a variable used in more than one pattern is a join condition. No JOIN, no ON. Here is the same question over the Aurora tables:

SELECT c.full_name, a.city
FROM   c360.customer c
JOIN   c360.address  a ON a.id = c.location;

The SPARQL never mentions the key columns location and id. In the graph, :address is not a key to match but an arrow pointing straight at the address. You do not join on it, you follow it.

The shared variable is a hash join: build a Map keyed on the join value, then look each row up in it. ?customer and ?addr are the keys.

SPARQL

?customer :name    ?name .
?customer :address ?addr .
?addr     :city    ?city .

Java 21

Map<String, Object> addrOf = graph.stream()
    .filter(t -> t.p().equals(":address"))
    .collect(Collectors.toMap(Triple::s, Triple::o));
Map<String, Object> cityOf = graph.stream()
    .filter(t -> t.p().equals(":city"))
    .collect(Collectors.toMap(Triple::s, Triple::o));

var rows = graph.stream()
    .filter(t -> t.p().equals(":name"))
    .filter(t -> cityOf.containsKey(addrOf.get(t.s())))
    .map(t -> List.of(t.o(), cityOf.get(addrOf.get(t.s()))))
    .toList();

Where the analogy breaks: Collectors.toMap assumes one value per key and throws on a duplicate. RDF has no such rule: a customer with two :address triples gives one row per combination. And the planner, not you, picks the build side and join order.

The WHERE block is a small graph with some nodes left blank; the engine reports every place it fits the big graph exactly. An empty result almost always means one arrow in your shape does not exist under that exact name: a typo, a wrong prefix, or the wrong graph.

4.4GRAPH: which folder to look in

Named graphs are folders of triples (Chapter 3). A Stardog query with no GRAPH keyword reads only the default graph (unless the database option query.all.graphs is switched on; it is off by default and this book assumes it stays off). Our practice data lives in the folder <urn:book:ch04>, so every query in this chapter names it:

SELECT ?customer ?name
WHERE {
  GRAPH <urn:book:ch04> {
    ?customer :name ?name .
  }
}

GRAPH <iri> { … } is SPARQL's nearest thing to the c360. in FROM c360.customer. GRAPH ?g { … } searches every folder, with ?g naming the one each match came from. In Chapter 9 this keyword is the heart of federation: one GRAPH block aimed at Aurora, another at Redshift, in one query.

Two differences deserve a warning. There is no fixed column list: a thing has whatever triples it has, and a query asks only for the ones it names. And there is no NULL: a missing value is simply an absent triple. Section 4.7 shows what that does to LEFT JOIN, and Chapter 5 why it matters.

4.6FILTER: row conditions, and why datatypes matter

Row conditions go in a FILTER inside WHERE. Filters compare numbers, strings and dates, combine with &&, || and !, and call functions such as CONTAINS, STRSTARTS, REGEX and YEAR:

?order :purchasePrice ?price ;
       :purchaseDate  ?date .
FILTER (?price > 1000 && ?date >= "2015-01-01"^^xsd:date)

Here Chapter 3's datatypes pay off. ?price > 1000 compares numerically only because the price is an xsd:decimal. Store it as the string "10479.00" and the comparison errors for that row, and the trap is that an error inside a filter does not stop the query: it counts as "not true", and the row silently disappears. (The semicolon is Turtle's "same subject, another predicate": two patterns sharing ?order, so a join.)

4.7OPTIONAL: LEFT JOIN without NULLs

OPTIONAL keeps a row even when part of the pattern has no match, like LEFT JOIN:

?c a :Customer ;
   :name ?name .
OPTIONAL { ?c :phone ?phone }

With no phone triple, the row stays and ?phone is unbound: an empty cell in Studio. Unbound is not a value; ?phone = "" will not find it. Test with FILTER (!BOUND(?phone)).

An unbound variable is closer to Optional.empty() than to null: the row survives, the slot is empty, and you test it (BOUND / isPresent()) instead of comparing it to a value.

SPARQL

?c a :Customer ;
   :name ?name .
OPTIONAL { ?c :phone ?phone }

# only the ones with no phone:
FILTER (!BOUND(?phone))

Java 21

record Row(String iri, String name, Optional<String> phone) {}

// OPTIONAL: every customer stays, phone may be empty
List<Row> all = customers.stream()
    .map(c -> new Row(c.iri(), c.name(),
            Optional.ofNullable(phoneOf.get(c.iri()))))
    .toList();

// a plain pattern is an inner join: no phone, no row
var withPhone = all.stream()
    .filter(r -> r.phone().isPresent()).toList();
// FILTER (!BOUND(?phone))
var noPhone = all.stream()
    .filter(r -> r.phone().isEmpty()).toList();

Where the analogy breaks: an Optional holds at most one value; two :phone triples would give two rows. And unbound does not mean "has no phone" (Chapter 5's open world), only that no phone triple is in the graph you queried.

The classic SQL-person bug: adding ?c :phone ?phone . to a customer report "just to show the phone". Every customer without a phone vanishes. If a column is nice-to-have, wrap it in OPTIONAL.

4.8Aggregates, ASK, and changing data

Aggregates work as in SQL (COUNT, SUM, AVG, MIN, MAX, and GROUP_CONCAT for string_agg), with one spelling rule: in SELECT an aggregate goes in parentheses with a name, (SUM(?price * ?qty) AS ?spend). That formula is the SUM(price * quantity) behind the book's headline number, Carolyn Inworth's $502,529.42. SELECT DISTINCT matters because following arrows multiplies rows: "cities of customers who ordered" gives one row per order without it. And put a LIMIT on exploratory queries; from Chapter 9 on, they reach a Redshift cluster that bills by the second.

GROUP BY with SUM is Collectors.groupingBy with a summing collector; ORDER BY DESC(...) LIMIT is sorted(...).limit(...). BigDecimal, because this is money.

SPARQL

SELECT ?name (SUM(?price * ?qty) AS ?spend)
WHERE {
  ?order :purchasedBy   ?customer ;
         :purchasePrice ?price ;
         :quantity      ?qty .
  ?customer :name ?name .
}
GROUP BY ?name
ORDER BY DESC(?spend)
LIMIT 3

Java 21

record Order(String name, BigDecimal price, int qty) {}

Map<String, BigDecimal> spend = orders.stream()
    .collect(Collectors.groupingBy(Order::name,
        Collectors.reducing(BigDecimal.ZERO,
            o -> o.price().multiply(BigDecimal.valueOf(o.qty())),
            BigDecimal::add)));

var top3 = spend.entrySet().stream()
    .sorted(Map.Entry.<String, BigDecimal>comparingByValue()
                     .reversed())
    .limit(3)
    .toList();

Where the analogy breaks: the obvious Collectors.summingDouble would reproduce the cent drift from Chapter 3; SPARQL sums xsd:decimal exactly, like BigDecimal. And the Java runs as written, while the SPARQL planner may reorder patterns, use indexes, or (from Chapter 9 on) push the whole SUM down into Redshift as SQL.

Two more query forms: ASK returns only true or false ("does this shape exist anywhere?"), and CONSTRUCT returns new triples built from a template instead of a table.

Writes use SPARQL Update, and you need three statements: INSERT DATA adds literal triples (no variables; think INSERT … VALUES), DELETE DATA removes exactly the triples you list, and DROP GRAPH empties a whole named graph (how every scratch exercise cleans up).

A graph is a set of triples. Inserting a triple that is already there changes nothing: no duplicate, no error. INSERT DATA is safe to rerun, but there is no "1 row inserted" signal; check with a COUNT.

"Every customer and their name." ?customer a :Customer means "things of type Customer"; a is short for rdf:type, the star of Chapter 5.

Query 2: a filter

"Which orders have a price above 1,000?"

Check yourself

What is SPARQL, and why not just use SQL on a table of triples?

The W3C query language (and HTTP protocol) for RDF. In a three-column SQL table every hop is another self-join, and SQL knows nothing about IRIs, typed literals or named graphs. SPARQL makes "follow this arrow" the basic operation.

In SPARQL, what plays the role of JOIN … ON a.k = b.k?

Using the same variable in two or more triple patterns: all must match the same value, an equi-join. You follow the arrow instead of matching key columns.

You add ?c :email ?email . to a working customer report and three customers disappear. Why, and how do you fix it?

Every plain pattern is an inner join, so customers with no email triple drop out. Wrap it: OPTIONAL { ?c :email ?email }.

A query with no GRAPH keyword returns nothing, though you know the data is there. The likely cause?

The triples are in a named graph, and without GRAPH Stardog reads only the default graph (query.all.graphs is off by default). Add GRAPH <urn:book:ch04> { … }, or GRAPH ?g { … } to search every named graph.

When would FILTER (?price > 1000) silently return nothing?

When the prices are plain strings, not typed numbers. Comparing a string with a number is an error, and a filter error counts as false: the rows vanish silently.

Chapter recap

  • SPARQL is the W3C query language and protocol for RDF; every Stardog database is a SPARQL endpoint.
  • A query is a picture of triples with blanks; each place it fits is one row.
  • A variable shared between patterns is a join: you follow arrows, never key columns.
  • GRAPH <iri> picks the folder. FILTER needs correct datatypes, and its errors silently drop rows.
  • OPTIONAL is LEFT JOIN; there is no NULL, only unbound variables and absent triples.
  • Aggregates, DISTINCT, ORDER BY and LIMIT work as in SQL. INSERT DATA is idempotent because a graph is a set.
  • On two orders each, Marlane Shadwick (344,866.50) outspent Carolyn Inworth (222,056.00). You then dropped <urn:book:ch04>.
