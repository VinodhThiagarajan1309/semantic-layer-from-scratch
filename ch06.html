Chapter 6

The T-Box, part 2: properties and the c360 ontology (OWL)

Relationships and attributes, the domain-and-range trap that catches every SQL person, and a tour of the complete c360 model, which you will load into Stardog by the end of the chapter.

One line in an ontology can look like a check but isn't. Take :purchasedBy rdfs:domain :Order. A property's domain is the kind of thing the property is used on: the subject, the left-hand side of the triple (Section 6.2 covers it properly). The line reads like "only orders can have :purchasedBy." What it actually tells Stardog is: "if something has :purchasedBy, label it an Order." So if bad data says Wax Paper :purchasedBy Carolyn, Stardog doesn't refuse it. With reasoning on, it quietly labels Wax Paper an Order. That is wrong: Wax Paper is a product. This chapter shows why it happens, how the c360 kit avoids it, and ends with the full ontology (161 triples) loaded as build step 2.

6.1Properties: the columns and foreign keys of a graph

The ten classes from Chapter 5 have no columns: our :Customer has no name, no email, no address. That is deliberate. In a graph, columns and foreign keys are played by a property: anything used as the predicate of a triple, such as :firstName or :purchasedBy. A property has its own IRI and is declared on its own, outside any class, so that many classes can share it and the model can say things about the property itself (its label, what it connects). OWL splits properties into two kinds:

  • An object property (owl:ObjectProperty) links a thing to another thing, an IRI you can keep following. order :purchasedBy customer:225. This is your foreign key.
  • A datatype property (owl:DatatypeProperty) links a thing to a literal (string, number, date). customer:225 :firstName "Carolyn". This is your plain column.

The analogy has three limits. A property is not owned by a table: one :name serves customers, products, categories and vendors, where SQL has four unrelated name columns. There is no cardinality by default: zero, one or five values are all fine (open world). And many-to-many needs no join table; you just write more triples.

Where does the real c360 vocabulary come from? The c360 knowledge kit (Chapter 1) ships its whole ontology as one Turtle file, schema.ttl, in Stardog's public GitHub repository: https://github.com/stardog-union/knowledge-kits/blob/main/examples/c360/models/schema.ttl. You'll load all of it at the end of this chapter. Here is its entry for :firstName, unchanged:

:firstName a owl:DatatypeProperty ;
    rdfs:label "first name" ;
    so:domainIncludes :Customer ;
    so:rangeIncludes xsd:string .

The last two lines say which class the property is used on (Customer) and what kind of value it takes (a string). so: is short for schema.org, a shared vocabulary for describing data on the web. The textbook way to write these two facts is rdfs:domain and rdfs:range, but that way has a trap (the Wax Paper problem from the opening). Sections 6.2 and 6.3 show the trap and why the kit uses so: instead.

A datatype property is a String, int or LocalDate field; an object property is a reference to another object. The big difference is where the property lives.

OWL (Turtle)

:firstName   a owl:DatatypeProperty .
:purchasedBy a owl:ObjectProperty .

# declared once, outside any class,
# usable on anything:
:name so:domainIncludes :Customer, :Product,
                        :Category, :Vendor .

Java 21

class Customer {
    String firstName;        // datatype property
}
class Order {
    Customer purchasedBy;    // object property
}

// nearest thing to a free-standing property:
interface Named { String name(); }
record Product(String name) implements Named {}
record Vendor(String name)  implements Named {}

Where the analogy breaks: a Java field belongs to its class. A property has its own IRI, and any subject may use it, with no implements to write. It is multi-valued by default, so :firstName behaves more like a List<String>. And the property is itself queryable data, like java.lang.reflect.Field stored next to the values.

6.2rdfs:domain and rdfs:range: rules, not checks

RDFS attaches a property to classes with rdfs:domain (the class of the subject) and rdfs:range (the class of the object). :purchasedBy rdfs:domain :Order ; rdfs:range :Customer . Every SQL person reads that as a constraint: "only orders may have :purchasedBy, and its value must be a customer." That reading is wrong, and why is the most useful idea in this chapter.

In RDFS, domain and range are inference rules:

  • If P rdfs:domain C and the graph has x P y, conclude x a C.
  • If P rdfs:range D and the graph has x P y, conclude y a D.

Nothing is ever rejected. In an open world (Chapter 5) the reasoner assumes the data is right and the type merely unstated, so it fills it in.

It gets worse when a property is shared, like the kit's :name. Written with rdfs:domain:

:name rdfs:domain :Category, :Customer, :Product, :Vendor .   # do NOT do this

Several domains do not mean "one of these". Each is its own rule and each fires, so every named thing becomes a Category and a Customer and a Product and a Vendor; Carolyn would become a product. (The formal fix, an owl:unionOf class as the domain, is heavy and still an inference rule, not a check.)

A Java developer reads rdfs:domain :Order as a parameter type the compiler enforces. What RDFS actually does is closer to the second method on the right.

RDFS (reasoning on)

:purchasedBy rdfs:domain :Order .

# a buggy loader writes:
product:268 :purchasedBy customer:225 .

# the reasoner does not reject it.
# It concludes:
product:268 a :Order .

Java 21

// What you expect "domain" to mean:
void purchasedBy(Order o, Customer c) { /* ... */ }
// purchasedBy(waxPaper, carolyn);  // compile error

// What rdfs:domain really does:
void assertTriple(Object s, String p, Object o) {
    if (p.equals(":purchasedBy")) {
        types.computeIfAbsent(s, k -> new HashSet<>())
             .add("Order");  // no check: s is now an Order
    }
    triples.add(List.of(s, p, o));
}

Where the analogy breaks: Java would call this a bug: nothing in Java changes an object's type because of how it was used. var inference works from a declaration at compile time; rdfs:domain infers from the data at query time. The check you expected exists, but it is SHACL (Chapter 11), not RDFS.

Remember: rdfs:domain and rdfs:range add types; they never reject data. To enforce "orders must be purchased by a customer", write a SHACL shape (Chapter 11).

6.3so:domainIncludes and so:rangeIncludes: the kit's answer

The c360 kit avoids the trap by not using rdfs:domain and rdfs:range at all. It uses two predicates from schema.org (prefix so: = https://schema.org/), the search engines' vocabulary for describing web content:

  • so:domainIncludes: "this property is expected on things of this class." Several values mean "any of these", which is what people mean.
  • so:rangeIncludes: "values are expected to be of this class or datatype."

The key word is expected. These predicates have no formal meaning in RDFS or OWL, so Stardog's reasoner draws no conclusions from them. :name so:domainIncludes :Category, :Customer, :Product, :Vendor says what the modeler meant, and reasoning in Chapter 10 will never make Carolyn a product.

They are documentation that machines can read. Stardog Designer writes them when you draw a property between two classes, and model views use them to show which properties belong to which class. Voicebox and your agent read them when writing SPARQL; so:domainIncludes :Customer is exactly the hint that :email belongs on a customer. (How each tool uses them internally is up to that tool; if a view looks empty, tell Claude.)

In a federated semantic layer you do not own the data. Inference rules that re-type things based on whatever Aurora and Redshift return are a liability: one bad row upstream changes your model's meaning. Descriptive "includes" predicates leave enforcement to SHACL (Chapter 11) and inference to rules you write on purpose (Chapter 10).

6.4owl:inverseOf, and a wrinkle in the kit

Every relationship reads two ways: "order purchased by customer" is also "customer placed order". SPARQL can already walk an arrow backward (?order :purchasedBy customer:225), but sometimes you want a name for the reverse direction. owl:inverseOf says two properties are one relationship read in opposite directions: if P owl:inverseOf Q, then x P y holds exactly when y Q x does. A correct example (not in the kit): :placedOrder owl:inverseOf :purchasedBy.

owl:inverseOf is a bidirectional JPA relationship: @ManyToOne on one side, @OneToMany(mappedBy = …) on the other.

OWL (reasoning on)

:placedOrder owl:inverseOf :purchasedBy .

# store only one direction:
order:1 :purchasedBy customer:225 .

# the other is implied:
SELECT ?o
WHERE { customer:225 :placedOrder ?o }

Java 21 + JPA

@Entity class Order {          // @Id omitted
    @ManyToOne
    Customer purchasedBy;      // owning side (the FK)
}
@Entity class Customer {
    @OneToMany(mappedBy = "purchasedBy")
    List<Order> placedOrders;  // inverse side
}
// in memory you keep both sides in sync yourself:
order.purchasedBy = carolyn;
carolyn.placedOrders.add(order);

Where the analogy breaks: JPA keeps the two directions consistent in the database but not in memory, hence every codebase's addOrder() helper. With owl:inverseOf there is nothing to sync: one triple is stored and the reverse derived at query time, only with reasoning on. The flip side: a wrong inverse, like the kit wrinkle below, produces wrong facts silently instead of failing at startup like a bad mappedBy.

An inverse must swap the two ends. Now read what schema.ttl actually says:

:rewardsAccountUsed a owl:ObjectProperty ;
    owl:inverseOf :hasRewards ;
    so:domainIncludes :Order ;
    so:rangeIncludes :RewardsAccount ;
    rdfs:label "rewards account used" .

:hasRewards a owl:ObjectProperty ;
    owl:inverseOf :rewardsAccount ;
    so:domainIncludes :Customer ;
    so:rangeIncludes :RewardsAccount ;
    rdfs:label "has rewards account" .

Both owl:inverseOf triples deserve a raised eyebrow. :rewardsAccountUsed goes Order → RewardsAccount and :hasRewards goes Customer → RewardsAccount: both point at the account, so they are not each other's reverse. Taken literally with reasoning on, "order O used account R" implies "R has rewards O". The second, :hasRewards owl:inverseOf :rewardsAccount, is sensible in intent (the account points back at its customer), but :rewardsAccount is declared nowhere and no mapping produces it; the open world allows that.

We load the kit exactly as shipped, because the rest of the book assumes that file, and with reasoning off (until Chapter 10) inverse axioms have no effect. The practical risk is contained but real: 1,560 of the 2,500 purchases carry a rewards account (none of Carolyn's do), so with reasoning on under this schema each of them yields a bogus inferred triple, and a query that also requires ?c a :Customer filters those rows out. Chapter 10 shows how to spot them. The lesson: an ontology is code, and code has bugs. If rewards accounts ever show up where customers should be in a reasoning query, look here first.

6.6What the ontology does not contain

Notice what schema.ttl does not mention: Aurora, Redshift, table or column names, cid, connection strings, SQL. It does not know there are 2,500 orders, or contain a single customer. It is purely a description of meaning: these kinds of things exist, and this is how they relate.

That separation is the point. Connecting meaning to where the data lives is the job of the mappings (Chapter 8 for Aurora, Chapter 9 for Redshift): "each row of c360.customer is a :Customer, and its first_name column is :firstName". Swap Redshift for Snowflake tomorrow and not one triple of the ontology changes; only a mapping does.

The flip side: model and mappings can drift apart, and the open world will not warn you. The Redshift mapping writes a vendor :homepage the ontology never declares, and no mapping produces the declared customer :thumbnail. A declaration is a promise of meaning, not a guarantee of values.

Compare: eight tables across two databases, about 40 columns with storage-flavored names (cid, dept, brand). The ontology has 10 classes and 33 properties named for a reader: :purchasedBy, not cid. That is the semantic layer's "one definition" promise: one agreed name per concept, used by every query, tool and agent.

Stardog's reasoner supports a practical subset of OWL (default level SL) plus its own rules, which express business logic such as "big spender" (Chapter 10). In one line: RDFS names things and arranges them in hierarchies, OWL describes relationships precisely, and neither validates.

The blog's ontology section is exactly this model, drawn in Stardog Designer and shared by mappings, reasoning, Voicebox and the agent. Two later sections hang off it: the named-graph security demo protects the properties marked m:SensitiveProperty, and the agent's system prompt (Path A) carries "a compact ontology summary", essentially Section 6.5's two tables condensed, which you write in Chapter 14.

  GRAPH <urn:stardog:training-c360:1.0:model> {

              rdfs:label ?label ;

Part C: register the model as a reasoning schema. A reasoning schema names one or more named graphs that Stardog treats as T-Box when reasoning. The database option reasoning.schemas holds a list of name=graph entries. Set it to exactly:

c360_schema=urn:stardog:training-c360:1.0:model

In Studio, open Databases, select kit-c360, and open its Properties. Find reasoning.schemas (in the reasoning group; the filter box helps), enter the value above as its single entry, and save. An earlier install of the c360 kit used this exact value on this database; Chapter 10 extends c360_schema with a second entry for the rules.

If Studio says the property can only be changed while the database is offline, do not take it offline yourself; stop and tell Claude the message.

Check: reopen the Properties panel and confirm that reasoning.schemas shows c360_schema=urn:stardog:training-c360:1.0:model. Query results do not change yet, because reasoning is still off.

Check yourself

Is :hasRewards an object or a datatype property, and what is its SQL counterpart?

An object property: its value is a RewardsAccount node. Its SQL counterpart is the foreign key rewards_account.cid, read the other way (customer to account).

Hypothetically the model says :quantity rdfs:range xsd:integer, and someone loads order :quantity "lots". What does Stardog do?

It stores the triple: rdfs:range is an inference rule, not a check. To have the value reported, write a SHACL shape with sh:datatype xsd:integer (Chapter 11).

Why would :name rdfs:domain :Category, :Customer, :Product, :Vendor be a bug, when the kit's so:domainIncludes version is fine?

Each rdfs:domain triple is a separate rule, so with reasoning on every named thing would become all four classes. so:domainIncludes only documents "any of these"; the reasoner ignores it.

Where in the ontology does it say that customers come from Aurora?

Nowhere. The ontology describes meaning only; the mappings (Chapters 8 and 9) connect classes and properties to physical data.

Why is :rewardsAccountUsed owl:inverseOf :hasRewards suspicious?

An inverse must swap the ends. Both properties point at a RewardsAccount, so they are not each other's reverse; with reasoning on, rewards accounts would "have rewards" orders.

You load schema.ttl on top of the 34 triples you typed. Why 161 and not 195?

The 34 typed triples are identical to triples in the file, and a graph is a set, so re-inserting them adds nothing.

Chapter recap

  • Object properties link things to things (foreign keys); datatype properties link things to literals (columns). Properties stand alone and can be shared.
  • rdfs:domain and rdfs:range are inference rules that add types and never reject data; several domains mean all of them at once.
  • The kit uses so:domainIncludes / so:rangeIncludes: descriptive, "any of these", ignored by the reasoner, read by tools and AI.
  • owl:inverseOf names a relationship's reverse. The kit's two inverse axioms are questionable, harmless with reasoning off.
  • The c360 ontology: 10 classes, 11 relationships, 22 attributes, 161 triples; :ssn and :cardNumber are marked sensitive.
  • The ontology knows nothing about Aurora or Redshift; mappings (Chapters 8 and 9) connect it to data.
  • Build step 2 is done: the full model (161 triples) in <urn:stardog:training-c360:1.0:model>, registered as reasoning.schemas = c360_schema=urn:stardog:training-c360:1.0:model.
