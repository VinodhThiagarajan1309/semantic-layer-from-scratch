Chapter 12

Governance: same question, different answers

Users, roles and permissions in Stardog, and how one switch makes the PII graph vanish for marketing while HR still sees it.

Two colleagues paste the same SPARQL into Studio at the same moment: "show me Jolynn Bithany's name and SSN." Priya from HR gets Jolynn Bithany | 609-38-5573. Marco from marketing gets Jolynn Bithany | with an empty cell. No error, no "access denied": for Marco, the part of the graph that holds SSNs simply doesn't exist. Nobody wrote a second query, a masked view, or a GRANT in Aurora. By the end of this chapter you'll have built exactly that, and your Chapter 14 agent inherits it for free: an LLM running as marketing that asks for SSNs gets nothing to leak.

12.1Five terms, broken down

TermWhat it isWhy it existsTiny example
UserA login on the Stardog server (username + password).Every request is made as someone.stardog_admin, and soon hr_user
RoleA named bundle of permissions that users are assigned to.You change a policy in one place, not per person.marketing
PermissionA triple of action + resource type + resource.To say exactly what may be done to what.read + db + kit-c360
Named-graph securityA database option that makes each named graph a separately permissioned resource.So access can be narrower than "the whole database."read on named-graph:kit-c360\virtual://aurora_c360_safe
Sensitive propertyA property whose values are masked for users without explicit permission.Hides one column-like property wherever it appears, without splitting graphs.:ssn shows as a masked string for marketing.

You know this pattern from Postgres: a user is a login role, a Stardog role is a group role, and a permission is a GRANT, so GRANT SELECT ON c360.customer TO marketing becomes read on a named graph. The differences: Stardog grants are on graphs (or sensitive properties), not tables or columns, and apply to meaning that can span two warehouses. And a graph you can't read doesn't raise "permission denied"; it silently disappears from your query, closer to row-level security than to a failed SELECT.

Roles and permissions work like Spring Security: you declare them, and the framework enforces them before your code runs.

Stardog

role  hr
  read · db          · kit-c360
  read · named-graph · kit-c360\virtual://aurora_c360_safe
  read · named-graph · kit-c360\virtual://aurora_c360_pii
user  hr_user  → role hr

Java

@PreAuthorize("hasRole('HR')")
public String ssn(int cid) {
  return customerRepo.ssn(cid);
}
// marketing_user → AccessDeniedException

Where the analogy breaks: @PreAuthorize guards a method and throws. Stardog guards data (graphs) whichever query touches it, and for GRAPH/FROM silently removes the graph; only SERVICE throws.

12.2The Stardog security model

Stardog's docs define a permission as an action on a resource of some resource type. The valid actions are read, write, create, delete, grant, revoke, execute, and all. The resource types you'll meet most:

Resource typeWritten as (CLI)Controls
dbdb:kit-c360querying / updating a database
named-graphnamed-graph:kit-c360\<graph IRI>one graph, only if named-graph security is on
virtual-graphvirtual-graph:virtual://namemanaging a virtual graph's definition
data-sourcedata-source:data-source://namemanaging a JDBC data source
sensitive-propertiessensitive-properties:kit-c360seeing unmasked sensitive values
metadata, admin, dbms-admin, stored-query, icv-constraints…database options, admin tasks, and the rest

Your server (read with a read-only API call) has two roles. cloud has every action on every resource type and belongs to stardog_admin, which is why nothing in this chapter locks you out. reader has read on db, named-graph, virtual-graph, data-source, metadata, stored-query and icv-constraints, all with the wildcard *. Remember that named-graph * line; it comes back in a gotcha.

12.3Named-graph security, and why virtual graphs are covered

By default a user who can read a database can read every graph in it. The option security.named.graphs changes that: "If enabled, named graphs are an explicit resource type in Stardog's security model." It's false by default and on kit-c360 today, and can be changed while the database is online. Once it's on:

  • A graph permission is written named-graph:<db>\<graph IRI>, with a backslash between database and graph. The docs' example is stardog-admin user grant -a read -o 'named-graph:myDB\http://example.org/g1' myUser.
  • Only read and write apply to named graphs, and "Wildcards cannot be used to grant permissions over named graphs," so you list each graph.
  • Graphs a user can't read are "silently dropped from the RDF dataset for the query," with no error.

Do virtual graphs count? Yes. The docs' Virtual Graph Security page says "Accessing virtual graphs is controlled the same way as regular named graphs": with named-graph security off, all virtual graphs are accessible, and with it on, "users will be able to query only the virtual graphs for which they have been granted access." So the permission for our PII graph is read on named-graph:kit-c360\virtual://aurora_c360_pii. (That exact string isn't printed on the page; it follows from the named-graph format. If Studio rejects it, tell Claude.) The same page distinguishes query forms:

How the query names the graphUser lacks permission →
GRAPH <virtual://aurora_c360_pii> { … }treated as empty, no error
FROM <virtual://aurora_c360_pii>treated as empty, no error
SERVICE <virtual://aurora_c360_pii> { … }an error

The silent disappearance is closer to a Hibernate @Filter switched on per session than to an access check.

What marketing effectively runs

SELECT ?name ?ssn WHERE {
  GRAPH <virtual://aurora_c360_safe> { … }
  OPTIONAL {
    GRAPH <virtual://aurora_c360_pii> { … }  # dropped
  }
}
# → Jolynn Bithany | (empty)

Java

@Entity
@FilterDef(name = "noPii")
@Filter(name = "noPii", condition = "1 = 0")
class CustomerPii { … }

session.enableFilter("noPii");  // marketing
// queries on CustomerPii return nothing,
// no exception

Where the analogy breaks: a Hibernate filter lives in one application and one database. Stardog enforces the permission in the data layer, for every client and every source behind it, so no application code can forget it.

This is why Chapter 8 split Aurora into aurora_c360_safe and aurora_c360_pii: security works per graph, and the PII mapping holds only :ssn and :cardNumber, so hiding that graph hides exactly those two properties.

This is the blog's section "Govern access with named-graph security." Its setup is the one you're building: aurora_c360_safe, aurora_c360_pii and redshift_c360, where hr_user has "Read on all three virtual graphs" and marketing_user has "Read on aurora_c360_safe and redshift_c360 only." When marketing asks for ?c :ssn ?ssn, "Stardog's planner treats aurora_c360_pii as if it did not exist for that user." In the blog's words: "Same SPARQL query, two roles, two different result sets." (The blog names both roles and users hr_user/marketing_user; we name the roles hr and marketing to tell them apart.)

12.4The alternative: sensitive properties

Splitting graphs means designing mappings around security. Stardog's other tool works per property: you list property IRIs in the database option security.properties.sensitive (named groups go in security.properties.sensitive.groups). Users without read on sensitive-properties:kit-c360 (or sensitive-properties:kit-c360\GroupName for a group) get the row with the value masked, by default as a SHA-256 hash. kit-c360 has a friendlier mask in security.masking.function: the string "Insufficient privileges to view this value".

So with security.properties.sensitive = tag:stardog:api:ecomm:ssn, marketing would see Jolynn Bithany | Insufficient privileges to view this value instead of an empty cell, arguably clearer because they learn the value exists. The blog describes this route as tagging :ssn as m:SensitiveProperty in the model (m: = urn:stardog:modules:); the server docs describe the database option, not that tag, so if you try it, set the option.

The docs say the sensitive-property feature "should not be considered production-ready": full-text search and zero-length property paths can bypass the mask, write permissions aren't restricted, and they don't say whether masking applies to virtual graphs. For real PII, use the graph split (what we built) as the control, and treat masking as a convenience on top.

12.5Why this beats per-warehouse grants, and where it doesn't

Grants in each warehouseNamed-graph security in Stardog
Where policy livesAurora GRANTs + Redshift GRANTs, kept in sync by handOne place, stated in business terms (the "PII graph")
Cross-warehouse questionsEach engine enforces its half; the join happens in someone's codeOne query, one policy, applied before any SQL is sent
An agent writing arbitrary queriesNeeds its own DB credentials per warehouseRuns as one Stardog user and can't reach what that user can't read
Adding a third source (say, Athena)A third grant systemOne more graph to permission

The honest limit: Stardog reaches Aurora and Redshift through the data sources' own logins (Chapter 7), so the warehouses see one service account, not Priya or Marco. Keep that account least-privileged (read-only on schema c360) and treat Stardog's roles as the per-person layer on top; warehouse controls stay as defense in depth. (Stardog can pass through a user's own credentials for some sources, such as Databricks with Microsoft Entra ID, but not in our setup.)

12.6Build step 6: two roles, two users, one query

Users and roles live in Studio → Security (the padlock in the left sidebar), available on your Free tier. Per the docs: + in the ROLES pane to add a role; select a role → Add Permission (action, resource type, resource); + in the USERS pane to add a user; select a user → Assign Role. And "When adding permissions via Studio, you can omit the resource type prefix," so you type kit-c360\virtual://aurora_c360_safe, not named-graph:kit-c360\….

1. Baseline, as stardog_admin. Run this in Studio (reasoning off). Expect one row, Jolynn Bithany | 609-38-5573 (fake data). Aurora may take about 20 s to wake.

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?name ?ssn
WHERE {
  VALUES ?c { <urn:stardog:demos:c360:customer:1> }
  GRAPH <virtual://aurora_c360_safe> { ?c :name ?name }
  OPTIONAL { GRAPH <virtual://aurora_c360_pii> { ?c :ssn ?ssn } }
}

2. Turn on named-graph security. Databases → kit-c360 → Properties, set security.named.graphs to true, save. Rerun step 1: unchanged, because stardog_admin's cloud role reads everything. (If the Free tier won't let you change this property, stop and tell Claude.)

3. Create role marketing and add these five permissions (action read, resource type db for the first and named-graph for the rest):

db           kit-c360
named-graph  kit-c360\virtual://aurora_c360_safe
named-graph  kit-c360\virtual://redshift_c360
named-graph  kit-c360\urn:stardog:training-c360:1.0:model
named-graph  kit-c360\urn:stardog:c360_extended_rules:1.0:model

The two model graphs expose the ontology, which Studio's Models view and Voicebox (Chapter 13) rely on.

4. Create role hr with the same five, plus a sixth:

named-graph  kit-c360\virtual://aurora_c360_pii

For reference only (you have no CLI here), the CLI form of one grant is stardog-admin role grant -n hr -a read -o 'named-graph:kit-c360\virtual://aurora_c360_pii'.

5. Create users hr_user and marketing_user, each with a password you choose and never paste into a chat. Assign role hr to hr_user and role marketing to marketing_user. Do not also assign the built-in reader role (see the gotcha below).

6. Run step 1's query as each user. Either add a Studio connection to your endpoint https://<your-endpoint>.stardog.cloud:5820 with that username and password, or use the terminal:

read -rs SDPW   # type marketing_user's password, press Enter (nothing is echoed)
curl -s -u "marketing_user:$SDPW" -H 'Accept: text/csv' \
  --data-urlencode 'query=PREFIX : <tag:stardog:api:ecomm:>
SELECT ?name ?ssn WHERE {
  VALUES ?c { <urn:stardog:demos:c360:customer:1> }
  GRAPH <virtual://aurora_c360_safe> { ?c :name ?name }
  OPTIONAL { GRAPH <virtual://aurora_c360_pii> { ?c :ssn ?ssn } } }' \
  https://<your-endpoint>.stardog.cloud:5820/kit-c360/query
unset SDPW

Expected:

Run asnamessn
stardog_adminJolynn Bithany609-38-5573
hr_userJolynn Bithany609-38-5573
marketing_userJolynn Bithany(empty)

7. See the two failure styles as marketing_user. Remove the OPTIONAL { … } wrapper (keep its inner GRAPH block) and you get zero rows, no error. Then change that GRAPH to SERVICE and you should get an error, as the Virtual Graph Security page describes.

These roles and users stay; they're part of the real build. To undo everything later, set security.named.graphs back to false and delete the two users and roles in Security.

  • The reader trap. The built-in reader role has read on named-graph *. Give it to marketing_user and the PII graph comes straight back: permissions only add up.
  • Silence is the failure mode. A typo in a permission's graph IRI doesn't error; the graph just comes back empty. If marketing_user gets no rows even for the name, check the spelling and the backslash first. If it's still empty, try also granting read on resource type virtual-graph with resource virtual://aurora_c360_safe (the built-in reader role includes that type, and the docs don't say whether querying needs it), then tell Claude which one fixed it.
  • No wildcards for graphs. A new virtual graph is invisible to both roles until you grant it.

Check yourself

What are the three parts of a Stardog permission? Give one from this chapter.

Action, resource type, resource. For example read · named-graph · kit-c360\virtual://aurora_c360_pii (CLI form named-graph:kit-c360\virtual://aurora_c360_pii).

Does named-graph security cover virtual graphs? What's your source?

Yes. The docs' Virtual Graph Security page says access to virtual graphs "is controlled the same way as regular named graphs."

Marketing runs GRAPH <virtual://aurora_c360_pii> { ?c :ssn ?ssn }. Error or empty? And with SERVICE?

GRAPH (and FROM) give an empty result with no error, because the graph is silently dropped from the dataset. SERVICE gives an error.

Why did Chapter 8 split Aurora into two virtual graphs?

Named-graph security grants whole graphs. Putting only :ssn and :cardNumber in aurora_c360_pii lets you hide exactly the sensitive properties by withholding one graph.

How would sensitive properties change marketing's result, and why aren't they our main control?

Marketing would get the row with the SSN masked ("Insufficient privileges to view this value" here). The docs call the feature not production-ready (full-text search and zero-length paths can bypass it) and don't say whether it covers virtual graphs.

Does Stardog security replace Aurora and Redshift grants?

No. The warehouses see only Stardog's data source login, which you keep read-only and least-privileged; Stardog roles are the per-person layer on top.

Chapter recap

  • Users get roles; roles hold permissions (action + resource type + resource). Your server has cloud (everything, on stardog_admin) and reader (read on everything, every named graph included).
  • security.named.graphs=true makes each graph a resource: named-graph:kit-c360\<IRI>, read/write only, no wildcards. Unreadable graphs are silently dropped.
  • Virtual graphs are covered the same way: GRAPH/FROM give empty results, SERVICE an error.
  • The safe/PII split from Chapter 8 is what makes graph-level security precise.
  • Sensitive properties mask values per property, but the docs say they aren't production-ready.
  • Build step 6 is done: roles hr and marketing, users hr_user and marketing_user, and the same SSN query returning 609-38-5573 for HR and an empty cell for marketing.
