Chapter 9

Federation: where the magic happens

Customers in Aurora, purchases in Redshift, one query. Who knows where the data lives, where SPARQL turns into SQL, and where the two halves finally meet.

Monday, 9:04 a.m. A message from your VP: "Who are our top spenders, and what state are they in? Need it for the 10 o'clock." Easy, you think, and open DBeaver. Then it sinks in. Names and states live in Aurora; purchases live in Redshift; no SQL statement you can type joins across both. You can answer the question, the slow way. By the end of this chapter you'll answer it with one query, and you'll be able to point at the exact place, inside Stardog, where the two databases meet.

9.1The slow way (do this once, so you feel it)

Here's the SQL-only route. First Redshift, which knows spend per customer number:

-- Redshift (dev.c360)
SELECT cid, SUM(price * quantity) AS spend
FROM c360.purchase
GROUP BY cid
ORDER BY spend DESC
LIMIT 3;

Top row: 225, 502529.42. Redshift has no idea who 225 is. So you copy the three cids out of the result grid and paste them into a second query, on Aurora:

-- Aurora (c360.c360). Paste the cids from the Redshift result.
SELECT c.cid, c.full_name, a.state
FROM c360.customer c
JOIN c360.address  a ON a.id = c.location
WHERE c.cid IN (225 /*, second cid, third cid */);

Then you match the two grids by eye. That last step is a join, and you are the join engine. It works for three rows. It doesn't work for "spend per state across all 500 customers", it can't be handed to an AI agent, and the usual ways out (a pipeline, Redshift federated query, a lake) all move data or bolt the two systems together. The rest of the chapter makes that go away.

9.2Who knows that customers are in Aurora and purchases are in Redshift?

Not the ontology, and not either database: the mappings, stored in Stardog as part of each virtual graph's definition. Here are the three layers you've built:

Each virtual graph is a name + a data source + a mapping, saved on the Stardog server (GET /admin/virtual_graphs lists them). The data source says which database (a JDBC connection, Chapter 7). The mapping's TO block says which ontology terms this graph can produce, and its FROM SQL says from which table. Together, a routing table: ":purchasedBy? That's the purchase block of redshift_c360. :name on a customer? The customer block of aurora_c360_safe."

Proof: this chapter's federated query never touches the T-Box. The mappings and the SPARQL mention :purchasedBy as the same plain IRI, and Stardog matches them. The ontology is still the shared vocabulary that reasoning and Voicebox depend on, but the "where" is entirely in the mappings. If you know Trino, layer 2 is its catalog, except it maps terms to tables.

9.3The Redshift mapping and the line that matters

Redshift needs its own virtual graph. The full redshift_c360.sms is in the Try box; here's the purchase block, the one that makes federation possible:

MAPPING <urn:c360:redshift:purchase>
FROM SQL {
  SELECT id, pid, "date" AS pdate, "time" AS ptime, quantity, price, cid, card, reward_account,
         CAST("date" AS varchar) || ' ' || "time" || ' - $' || CAST(price AS varchar) AS label
  FROM c360.purchase
}
TO {
  ?iri a :Order ; rdfs:label ?label ;
    :purchasePrice ?p ; :quantity ?q ; :purchaseTime ?ptime ; :purchaseDate ?dt ;
    :purchasedBy ?cust_iri ; :itemPurchased ?product ; :cardUsed ?cc ; :rewardsAccountUsed ?rewardsIri .
}
WHERE {
  BIND(TEMPLATE("urn:stardog:demos:c360:purchase:us:pos{id}") AS ?iri)
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?cust_iri)
  BIND(TEMPLATE("urn:stardog:demos:c360:product:{pid}") AS ?product)
  BIND(TEMPLATE("urn:stardog:demos:c360:cards:{card}") AS ?cc)
  BIND(TEMPLATE("urn:stardog:demos:c360:rewards:{reward_account}") AS ?rewardsIri)
  BIND(xsd:decimal(?price) AS ?p)
  BIND(xsd:integer(?quantity) AS ?q)
  BIND(xsd:date(?pdate) AS ?dt)
}

Chapter 8's tools read all of it: each row is an :Order; four foreign keys become four arrows; the label is concatenated in SQL; three casts pin the datatypes. The quoted "date" and "time" and the xsd:decimal each have a story (Section 9.9). But one line is the whole chapter:

BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?cust_iri)   -- Redshift, purchase block
BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?iri)        -- Aurora, customer block (Chapter 8)

Character for character, the same template. Redshift's purchase.cid = 225 and Aurora's customer.cid = 225 both become the IRI <urn:stardog:demos:c360:customer:225>, and in RDF a node is its IRI (Chapter 3). So Aurora's facts about customer 225 and Redshift's orders "purchased by" customer 225 are facts about one and the same node. As the Redshift DDL's comment puts it: the cross-engine "join" is the shared IRI template, not a foreign key.

The other three blocks (product, category, vendor) use the same ideas, with two details: vendors are matched by name (vendor:{brand} on products, vendor:{vendor_name} on vendors, percent-encoded because names contain spaces), and a product's list price stays xsd:float because the ontology declares :hasPrice as float and nothing ever sums it.

9.4Where exactly does SPARQL get converted to SQL?

Inside the Stardog server's query planner, before a byte goes to AWS. Studio just sends text over HTTPS, and Aurora and Redshift only run the SQL that comes out at the end. The planner, in order:

  1. Parse. The SPARQL text becomes an algebra tree: triple patterns, joins, a group, an order, a limit.
  2. Route each triple pattern to a mapping. Which mapping blocks have a matching pattern in their TO? ?o :purchasedBy ?c matches only the purchase block of redshift_c360; ?c :name ?name matches the customer block of aurora_c360_safe (layer 2 of Figure 9.1 at work).
  3. Group by source. Patterns answerable by the same virtual graph are bundled, because one SQL statement can answer the bundle. Bundled patterns that share a variable built from matching templates (customer :address ↔ address subject) become a SQL JOIN.
  4. Rewrite each bundle into the source's SQL dialect. Stardog's virtual-graph engine is built on Apache Calcite, an open-source SQL parser and query-algebra framework. Stardog uses it to parse your mapping's FROM SQL, combine it with the query's needs, and print SQL in Postgres or Redshift flavor. You've met Calcite already: Object 'customer' not found within 'c360' (Section 7.5) is its wording, and real query plans print Calcite operators such as LogicalProject and JdbcTableScan.
  5. Plan the rest. Whatever can't be pushed into a source (the cross-source join, and anything that depends on it) becomes Stardog operators above the SQL leaves.

Step 4's "do as much as possible in the source" is pushdown (introduced in Section 7.3): moving computation to the data is almost always cheaper than moving data to the computation.

For one source, this is what Hibernate does with HQL: the mapping plus a dialect print SQL, with the WHERE in the SQL instead of the JVM. Stardog's mapping is the entity annotation, Calcite is the Dialect, and pushdown is the where clause landing in the database.

SPARQL, and the SQL Stardog sends

GRAPH <virtual://aurora_c360_safe> {
  ?c :name ?name ; :address ?a .
  ?a :state "Texas" .
}

# Stardog (Calcite, Postgres dialect),
# roughly:
# SELECT c.full_name, a.state
# FROM c360.customer c
# JOIN c360.address a ON c.location = a.id
# WHERE a.state = 'Texas'

Java 21 + Hibernate

List<Object[]> rows = em.createQuery("""
        select c.fullName, a.state
        from Customer c join c.address a
        where a.state = :st""", Object[].class)
    .setParameter("st", "Texas")
    .getResultList();

// Hibernate (PostgreSQLDialect), roughly:
// select c1_0.full_name, a1_0.state
// from c360.customer c1_0
// join c360.address a1_0 on a1_0.id = c1_0.location
// where a1_0.state = ?

Where the analogy breaks: a Hibernate persistence unit has one DataSource and one dialect, so HQL cannot join an Aurora Customer to a Redshift Order. Stardog routes each pattern to its own source and dialect, then does the cross-source join itself (the Java version is in Section 9.6).

How Stardog knows which graphs to look in: GRAPH vs virtual transparency

Our queries name their sources with GRAPH <virtual://…> { … }. That's explicit routing: the patterns inside may only match that virtual graph. By default, a query with no GRAPH block reads the local default graph and does not see virtual graphs at all; you'd get zero rows. With the database option virtual.transparency=true, Stardog adds every virtual graph the user may access to the query's dataset, so you can drop the GRAPH blocks and each pattern is matched against whichever graph can answer it. One subtlety from the docs: a GRAPH ?g { … } block still forces all its patterns to match within one graph, so patterns split across Aurora and Redshift return nothing inside a single GRAPH ?g.

We keep explicit GRAPH blocks in this book: they make the routing visible and Chapter 12's security demo easy to reason about, and Chapter 14's agent uses them too.

9.5Sometimes Aurora, sometimes Redshift, sometimes both

Routing is per pattern, so the same endpoint sends SQL to one database, the other, or both, depending on which terms your query uses. Three examples from the blog's sample questions (SQL shown is illustrative; Section 9.8 shows how to see the real text):

Aurora only: customers by state

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?state (COUNT(?c) AS ?n)
WHERE { GRAPH <virtual://aurora_c360_safe> { ?c a :Customer ; :address ?a . ?a :state ?state } }
GROUP BY ?state ORDER BY DESC(?n) LIMIT 5

Every pattern routes to Aurora, so the whole thing, join, group, sort and limit, is pushed down as one statement, roughly SELECT a.state, COUNT(*) FROM customer c JOIN address a ON c.location = a.id GROUP BY a.state ORDER BY 2 DESC LIMIT 5. Redshift stays asleep. Five rows cross the wire (Texas 53, California 51, Florida 48, …; you ran this in Chapter 8).

Redshift only: top products by units sold

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?product (SUM(?qty) AS ?units)
WHERE { GRAPH <virtual://redshift_c360> { ?o :itemPurchased ?p ; :quantity ?qty . ?p :name ?product } }
GROUP BY ?product ORDER BY DESC(?units) LIMIT 10

All patterns route to Redshift. The purchase-to-product hop matches templates (product:{pid} ↔ product:{id}), so it becomes a SQL join, roughly SELECT p.name, SUM(u.quantity) FROM purchase u JOIN product p ON u.pid = p.id GROUP BY p.name ORDER BY 2 DESC LIMIT 10. Aurora stays paused.

Both: top spenders with their state

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?name ?state (SUM(?price * ?qty) AS ?spend)
WHERE {
  GRAPH <virtual://redshift_c360> {
    ?o a :Order ; :purchasedBy ?c ; :purchasePrice ?price ; :quantity ?qty .
  }
  GRAPH <virtual://aurora_c360_safe> {
    ?c :name ?name ; :address ?a .
    ?a :state ?state .
  }
}
GROUP BY ?c ?name ?state
ORDER BY DESC(?spend)
LIMIT 10

Now ?c appears in both blocks. Chapter 4 said "a shared variable is a join"; here the shared variable crosses two databases. Stardog sends one SQL statement to each side:

-- Illustrative: to Redshift. The mapping's SQL becomes a subquery; only needed columns are selected.
SELECT "cid", "price", "quantity"
FROM (SELECT id, pid, "date" AS pdate, "time" AS ptime, quantity, price, cid, card, reward_account,
             CAST("date" AS varchar) || ' ' || "time" || ' - $' || CAST(price AS varchar) AS label
      FROM c360.purchase) AS "t"
WHERE "cid" IS NOT NULL AND "price" IS NOT NULL AND "quantity" IS NOT NULL

-- Illustrative: to Aurora. The join condition location = id was derived from matching templates.
SELECT "t0"."cid", "t0"."full_name", "t1"."state"
FROM (SELECT cid, first_name, last_name, email, phone, location, full_name FROM c360.customer) AS "t0"
JOIN (SELECT id, city, state, zip, ... FROM c360.address) AS "t1" ON "t0"."location" = "t1"."id"

And here's the catch. The SUM is grouped by name and state, from Aurora, over prices from Redshift. Neither database has both, so neither can compute it. That brings us to the heart of the chapter.

9.6Where the data lands, and how the answer is rolled up

No database ever joins Aurora to Redshift. Stardog does, in memory, for the duration of one query. Press Play to follow it.

Step 10 answers "without a JOIN across two engines, how does the data come together?"

  • Where the rows land. Each SQL result streams back over JDBC into Stardog's query engine, where it lives in memory as bindings (variable → value rows, like a result set) for the life of this one query. Nothing is written into kit-c360. (Very large joins may spill to temporary disk; still scratch space, not stored data.)
  • How keys become the same key. Each Redshift row's cid goes through the purchase mapping's template and binds ?c to customer:225; each Aurora row's goes through the customer mapping's template to the same IRI. Because the templates are identical, Stardog can compare the underlying values rather than long strings, but logically it joins on the IRI.
  • How the join runs. Typically a hash join: build a hash table from the smaller side (500 customers, keyed by ?c), then stream the 2,500 purchase rows through it. The planner can also choose a bind join: run one side first, then send its keys into the other side's SQL (think WHERE cid IN (225, …)), which wins when one side is tiny, such as "top spenders in Wisconsin". The docs show plans combining virtual graphs under a ServiceJoin operator; the strategy is the optimizer's call, and your plan (Section 9.8) tells you.
  • Only then, the rollup. Stardog computes SUM(?price * ?qty) per customer (on exact xsd:decimal values), sorts, and keeps ten. An aggregate grouped by Aurora's columns over Redshift's numbers can't be pushed to either source.

Here is step 10 of Figure 9.2 by hand: two DataSources, one query each, a Map keyed by cid, then group, sum, sort and limit in the JVM. Without a semantic layer, you'd write and maintain this for every cross-database question.

SPARQL (the federated query, trimmed)

SELECT ?name ?state
       (SUM(?price * ?qty) AS ?spend)
WHERE {
  GRAPH <virtual://redshift_c360> {
    ?o :purchasedBy ?c ;
       :purchasePrice ?price ;
       :quantity ?qty .
  }
  GRAPH <virtual://aurora_c360_safe> {
    ?c :name ?name ; :address ?a .
    ?a :state ?state .
  }
}
GROUP BY ?c ?name ?state
ORDER BY DESC(?spend)
LIMIT 10

Java 21 (Spring JdbcTemplate)

record Order(int cid, BigDecimal price, int qty) {}
record Cust(String name, String state) {}
record Row(String name, String state, BigDecimal spend) {}

// A: Redshift, one row per order
List<Order> orders = redshift.query(
    "SELECT cid, price, quantity FROM c360.purchase",
    (rs, i) -> new Order(rs.getInt(1),
        rs.getBigDecimal(2), rs.getInt(3)));

// B: Aurora, customers with their state, keyed by cid
Map<Integer, Cust> byCid = aurora.query("""
        SELECT c.cid, c.full_name, a.state
        FROM c360.customer c
        JOIN c360.address a ON a.id = c.location""",
    (rs, i) -> Map.entry(rs.getInt(1),
        new Cust(rs.getString(2), rs.getString(3))))
    .stream()
    .collect(Collectors.toMap(Map.Entry::getKey,
                              Map.Entry::getValue));

// join on cid, then group + sum (exact decimals)
Map<Integer, BigDecimal> spend = orders.stream()
    .filter(o -> byCid.containsKey(o.cid()))
    .collect(Collectors.groupingBy(Order::cid,
        Collectors.reducing(BigDecimal.ZERO,
            o -> o.price().multiply(
                     BigDecimal.valueOf(o.qty())),
            BigDecimal::add)));

// sort + limit
List<Row> top10 = spend.entrySet().stream()
    .map(e -> { var c = byCid.get(e.getKey());
                return new Row(c.name(), c.state(), e.getValue()); })
    .sorted(Comparator.comparing(Row::spend).reversed())
    .limit(10)
    .toList();

Where the analogy breaks: the Java is frozen to this one question. Ask for "top spenders in Wisconsin" and you rewrite both SQL strings and choose the join strategy yourself; Stardog generates the SQL from the mappings, pushes down what it can (Section 9.7), and picks the join per query. And your code joins on a bare int cid, trusting both databases mean the same thing by it; in Stardog that agreement is written down as the shared IRI template.

The trade-offs, honestly

ConcernWhat it means here
Data volume on the wireAnything that can't be pushed down gets pulled: here one row per order. 2,500 rows is nothing; 2.5 billion would be a problem.
PushdownSingle-source work runs in the database; cross-source joins and anything above them run in Stardog. Query shape decides (next section).
LatencyAt least the slower source's time plus transfer. Our Aurora adds 15 to 20 seconds after a pause.
CostYou pay each source's compute per query (Redshift bills a 60-second minimum per wake-up) and Stardog's memory for the join.
FreshnessThe upside for all of the above: every run reads live data. No pipeline, no copy.

9.7Helping pushdown: put single-source work inside one source

You can restructure the query so most of the work is single-source: sum per customer inside Redshift first, then join the totals to Aurora:

PREFIX : <tag:stardog:api:ecomm:>
SELECT ?name ?state ?spend
WHERE {
  {
    SELECT ?c (SUM(?price * ?qty) AS ?spend)
    WHERE {
      GRAPH <virtual://redshift_c360> {
        ?o :purchasedBy ?c ; :purchasePrice ?price ; :quantity ?qty .
      }
    }
    GROUP BY ?c
  }
  GRAPH <virtual://aurora_c360_safe> {
    ?c :name ?name ; :address ?a .
    ?a :state ?state .
  }
}
ORDER BY DESC(?spend)
LIMIT 10

The subquery touches only Redshift, so Stardog can push the whole GROUP BY into it (roughly SELECT cid, SUM(price * quantity) FROM purchase GROUP BY cid), and Redshift returns about one row per customer instead of one per order. Same answer, far fewer rows. Whether your version pushes this aggregate is what the plan will tell you.

9.8Seeing the real plan

Figure 9.2 shows how Stardog works in general; your endpoint can show what it actually does. Studio's Workspace can show a query's plan (the docs call it the place to "write, execute, and see query plans"); look for a plan or explain control near Run. The CLI equivalent is stardog query explain. In the plan text, look for:

  • VirtualGraphSql<virtual://…>: one per SQL statement sent to a source. Query= is the exact SQL; Vars= shows columns becoming variables, e.g. ?c <- TEMPLATE(urn:stardog:demos:c360:customer:{cid}). Both leaves binding ?c with the same template is the IRI trick in the machine's own words.
  • A join above them (for example HashJoin(?c) or a ServiceJoin): the variable is the join key.
  • [#N]: the optimizer's row estimate for each node.

9.9Why the template is the join key, and the gotchas to watch for

Everything above depends on two independent mapping files agreeing on a string pattern. That contract breaks quietly:

  • Different templates: no error, no rows. If Redshift minted urn:c360:buyer:{cid}, the federated query would run and return nothing. The most common federation bug.
  • Different key formats. 225 vs 0225 vs C-225 give different IRIs. Normalize in the mapping's SQL.
  • Different meanings. A generic urn:node:{id} for both customers and products would merge unrelated things (the docs' optimization page has an example with actors and movies). That's why every c360 template names its type.

Quote reserved words. purchase has columns called date and time, both SQL reserved words. Redshift tolerates them bare, but Stardog parses the mapping's SQL itself (Calcite, Section 9.4), and the parse fails. Fix: "date" AS pdate, "time" AS ptime.

Pin types with casts. The kit's original mappings were written for CSV, where everything is a string, hence xsd:integer(?quantity) and xsd:date(…). Over SQL the columns are typed already, but explicit casts make each datatype match the ontology rather than whatever the driver reports; mismatched types break comparisons, YEAR() and value joins.

Money is xsd:decimal, never xsd:float. The kit's original mapping casts purchase prices with xsd:float, which puts Carolyn's total at $502,529.44, 2 cents off SQL (the float drift of Chapter 3). With xsd:decimal, matching Redshift's decimal(12,2), it matches SQL to the cent: $502,529.42.

On cost: batch your experiments. The first query after a pause waits 15 to 20 seconds for Aurora; each Redshift wake-up bills at least 60 seconds (at 4 RPUs, about 2.5 cents), and the 1 RPU-hour daily cap is roughly 15 minutes of compute. Fine for this book, not for a script in a loop, which is why Chapter 14's agent gets a LIMIT and a timeout.

The blog's federated sample, "Top ten customer spenders with their state", is the query in 9.5, and its key idea is this chapter's: an IRI template gives each customer one identity across Aurora and Redshift, so no ETL is needed. "Cooperation without coordination" follows: add Athena or another source later by minting the same IRIs, without touching existing mappings.

Check yourself

Who knows that customer names are in Aurora and purchases are in Redshift?

The virtual graph definitions stored in Stardog: a data source (which database) plus a mapping (which ontology terms come from which tables). Not the ontology, which only defines meaning, and not the databases.

Where exactly is SPARQL turned into SQL?

In the Stardog server's query planner: parse, route each triple pattern to the mapping blocks whose TO can produce it, bundle per source, and rewrite each bundle into that source's SQL dialect with Apache Calcite, pushing down as much as it can.

A query has no GRAPH blocks and returns zero rows, though the virtual graphs exist. Why?

By default, virtual graphs aren't in a query's dataset. Either name them with GRAPH <virtual://…> or enable the database option virtual.transparency, which adds all accessible virtual graphs.

Which databases receive SQL for (a) customers by state, (b) top products by units, (c) top spenders with state?

(a) Aurora only, fully pushed down. (b) Redshift only, fully pushed down. (c) Both: one statement each; the join, the SUM, the sort and the limit happen in Stardog.

Where do the rows land, and why can't the SUM be pushed to Redshift in the 9.5 query?

They stream into Stardog's memory as bindings for the life of the query; nothing is stored. The SUM is grouped by name and state, which only Aurora has, so it must follow the cross-source join. The 9.7 rewrite groups by ?c inside a Redshift-only subquery, which can be pushed.

What would you see if Redshift's mapping used urn:c360:buyer:{cid}?

No error and zero federated rows: no IRI would appear in both graphs, so the join on ?c matches nothing. Templates are the contract.

Chapter recap

  • No SQL statement spans Aurora and Redshift; by hand, it takes two queries and a human join.
  • Three layers: the ontology (meaning), the virtual graph definitions in Stardog (where), the databases (rows).
  • SPARQL becomes SQL in Stardog's planner: parse, route patterns to mappings, bundle per source, rewrite with Calcite, push down. Use explicit GRAPH blocks or turn on virtual.transparency.
  • Single-source queries are pushed down whole. Cross-source queries send one SQL per source, join the rows in Stardog's memory on the shared customer IRI (hash or bind join), then aggregate, sort and limit.
  • The IRI template is the join key: identical templates, identical key formats, type-specific names.
  • Gotchas: quote "date"/"time"; cast with xsd:integer/xsd:date; money as xsd:decimal (float drifted 2 cents).
  • Result: Carolyn Inworth, Wisconsin, $502,529.42; Marlane Shadwick, Florida, $491,217.53; Isaac Popping, Pennsylvania, $440,274.78, matching SQL exactly.
