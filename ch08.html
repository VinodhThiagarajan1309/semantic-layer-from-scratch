Chapter 8

Mappings: teaching Stardog to read your tables

How a few lines of mapping turn Aurora's customer rows into triples, and why we build two graphs instead of one.

Hand a new hire a printout of the customer table and ask what it means. They'll get most of it right by squinting at the headers: cid is probably an ID, location looks like a UUID pointing somewhere, ssn is scary. Stardog can't squint. After Chapter 7 it can reach Aurora, but it doesn't know which column is the key, which is a pointer, or which ontology property each feeds. A mapping is the note you'd staple to the printout: "run this SQL; for every row, produce these triples." You'll read one line by line, meet the IRI template that Chapter 9 depends on, and create your first two virtual graphs.

8.1What a mapping is

A mapping has an input, a SQL query, and an output, triple patterns with variables in them. For every row, Stardog fills the variables and emits the triples. For a virtual graph nothing is emitted in advance: the mapping is a recipe on file, and Stardog reads it backwards: when a query asks for ?c :email ?e, it looks up ":email comes from the email column of the customer SQL" and generates SQL to fetch just that.

Here is the smallest useful mapping, for Carolyn's email. It has three parts, each marked by a keyword:

MAPPING
FROM SQL {                                   # 1. input: a SQL query on Aurora
  SELECT cid, email FROM c360.customer
}
TO {                                         # 2. output: the triples to produce
  ?c :email ?email .
}
WHERE {                                      # 3. how to build the names
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?c)
}

For the row cid = 225, email = 'cinworth68@g.co', the FROM SQL part supplies the columns, the WHERE part turns 225 into the name customer:225, and the TO part produces the triple customer:225 :email "cinworth68@g.co". Section 8.3 goes through each part in detail.

So who knows that customers live in Aurora? Not the ontology (it only defines what :Customer means) and not Aurora (it's never heard of the ontology). The mapping does: it names ontology terms in its TO block and tables in its FROM SQL, and the virtual graph ties it to a data source. Chapter 9 draws this as three layers.

A mapping is like a CREATE VIEW whose output is triples with globally unique names. Postgres inlines a view's definition into your query; Stardog likewise inlines the mapping into the SPARQL query, then generates SQL. Where it stops: one mapping emits several kinds of fact per row (a type, properties, links), queried with SPARQL patterns, not column lists.

8.2Two languages: R2RML and SMS2

R2RML ("RDB to RDF Mapping Language") is the W3C standard for this job, portable between vendors but verbose: it is itself written as Turtle (rr:subjectMap, rr:predicateObjectMap, rr:column…), and a simple table takes twenty lines. Stardog reads it.

SMS2 (Stardog Mapping Syntax 2) is Stardog's own format: it looks like SPARQL's CONSTRUCT (Chapter 4) and also handles CSV and JSON. The docs recommend it, every mapping in this book uses it, and you select it with the virtual-graph option mappings.syntax=SMS2.

8.3The shape of an SMS2 mapping

An SMS2 file has a prologue (prefix declarations, exactly like Turtle and SPARQL) followed by one or more mapping blocks separated by semicolons. Each block has four parts:

  • MAPPING <iri> names the block, for humans and error messages; it doesn't appear in the data.
  • FROM SQL { … } is ordinary SQL in the source's dialect. Each output column becomes a variable: email becomes ?email.
  • TO { … } lists triple patterns using those variables, in the ontology terms you loaded in Chapters 5 and 6.
  • WHERE { … } creates new variables with BIND. For SQL sources, only two kinds of function are allowed: TEMPLATE(…) to build IRIs, and datatype casts such as xsd:integer(…), xsd:decimal(…), xsd:date(…) (plus strdt). Anything else, such as string concatenation, has to happen in the SQL.

Written in one order, run in another. A mapping is written FROM SQL → TO → WHERE, but it runs FROM SQL → WHERE → TO. And WHERE here does not filter rows the way SQL's WHERE does: it computes new values, like an extra expression in a SELECT. One row, step by step:

StepPartWhat happens to Carolyn's row
1FROM SQLSELECT cid, email FROM c360.customer gives cid = 225, email = 'cinworth68@g.co'
2WHEREBIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?c) fills the {cid} slot, so ?c = urn:stardog:demos:c360:customer:225
3TO?c :email ?email . writes the triple customer:225 :email "cinworth68@g.co"

The same three steps as one SQL statement:

SELECT 'urn:stardog:demos:c360:customer:' || cid AS c,  -- step 2 (WHERE / BIND)
       email                                             -- used in step 3 (TO)
FROM c360.customer;                                      -- step 1 (FROM SQL)
-- each result row then becomes the triple:  <c> :email "<email>"

In one line: FROM SQL is where the rows come from, WHERE builds the names (IRIs) from each row's key, and TO says which triples to write.

8.4The customer mapping, line by line

We will map Aurora's data into two virtual graphs. aurora_c360_safe holds everything except the sensitive values: Carolyn's name, email, phone and address go here. aurora_c360_pii holds only the sensitive ones (PII, personally identifiable information): her SSN 640-83-5765 (fake data) and full card numbers. Keeping them apart lets you later give Marketing the safe graph and HR both (Section 8.7 explains why, Chapter 12 does it).

Here is the first block of aurora_c360_safe.sms, the mapping file for the safe graph (.sms is just the file extension for Stardog Mapping Syntax, like .sql for SQL), exactly as it's used in the working build:

prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#>
prefix xsd: <http://www.w3.org/2001/XMLSchema#>
prefix : <tag:stardog:api:ecomm:>

MAPPING <urn:c360:aurora:customer>
FROM SQL { SELECT cid, first_name, last_name, email, phone, location, full_name FROM c360.customer }
TO {
  ?iri a :Customer ;
    :email ?email ; :firstName ?first_name ; :lastName ?last_name ;
    :phone ?phone ; :address ?loc_iri ; :name ?full_name ; rdfs:label ?full_name .
}
WHERE {
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?iri)
  BIND(TEMPLATE("urn:stardog:demos:c360:location:{location}") AS ?loc_iri)
}
LineWhat it does
prefix rdfs: …
prefix xsd: …		Short names for two standard vocabularies: rdfs:label (the human-readable name every tool displays) and the XML Schema datatypes used in casts (Chapter 3).
prefix : <tag:stardog:api:ecomm:>The c360 ontology's namespace: :Customer expands to <tag:stardog:api:ecomm:Customer>, the class you loaded in Chapter 5. Misspell it and the mapping still runs, but emits terms your ontology has never heard of.
MAPPING <urn:c360:aurora:customer>Names the block. Any unique IRI will do.
FROM SQL { SELECT cid, first_name, … FROM c360.customer }The "table" for this block. It lists columns explicitly and leaves out ssn and picture: this is the safe graph, so the SSN column is never even read. c360.customer resolves because the data source has sql.schemas=c360.
TO { … }The triples to emit per row.
?iri a :Customer ;Every row is a customer (a is rdf:type). The subject ?iri is built in the WHERE part below.
:email ?email ; :firstName ?first_name ; :lastName ?last_name ;Plain columns become datatype properties (Chapter 6) with literal values. Semicolons repeat the subject, as in Turtle.

WHERE { … }The derived variables. In the full file a ; follows, then the next MAPPING.

The address mapping mints its subjects with the same template from address.id, so the arrow lands on the right node.

An SMS2 mapping block does the job of a JPA entity mapping: FROM SQL is @Table, each variable is a @Column, the subject template is the @Id, and an object-property arrow built from a key column is a @ManyToOne with a @JoinColumn.

SMS2 (trimmed)

MAPPING <urn:c360:aurora:customer>
FROM SQL { SELECT cid, first_name, email, location
           FROM c360.customer }
TO {
  ?iri a :Customer ;
    :firstName ?first_name ;
    :email     ?email ;
    :address   ?loc_iri .
}
WHERE {
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?iri)
  BIND(TEMPLATE("urn:stardog:demos:c360:location:{location}")
       AS ?loc_iri)
}

Java 21 + JPA

@Entity
@Table(name = "customer", schema = "c360")
public class Customer {
    @Id
    @Column(name = "cid")
    private Integer cid;

    @Column(name = "first_name")
    private String firstName;

    private String email;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "location")
    private Address address;
}

Where the analogy breaks: JPA turns rows into objects in your JVM; a virtual-graph mapping never instantiates anything, it is read backwards to turn SPARQL into SQL, much as Hibernate turns HQL into SQL (Chapter 9). FROM SQL can be any SELECT (closer to @Subselect), and one block may describe several subjects (the rewards block below), which no entity class can do.

Where is the JOIN? Neither mapping has one. The customer mapping reads only c360.customer and writes customer:225 :address location:b80ea2ce… (template location:{location}). The address mapping (Section 8.6) reads only c360.address and writes location:b80ea2ce… :city "Milwaukee" (template location:{id}). Both templates produce the same string, urn:stardog:demos:c360:location:b80ea2ce…, so they are the same node: the matching name plays the part of customer.location = address.id. The JOIN happens when you query: ask for ?c :address ?a . ?a :city ?city and Stardog sends Aurora … FROM c360.customer c JOIN c360.address a ON a.id = c.location itself. Mappings stay one table each; Stardog writes the joins a query needs.

8.5IRI templates: the most important line in the file

An IRI is RDF's globally unique name for a thing (Chapter 3). An IRI template is a string with {column} placeholders that turns a row's local key into such a name: cid = 225 means nothing outside the customer table, but urn:stardog:demos:c360:customer:225 means one customer anywhere. Three things matter in practice:

  1. A template is a primary key and a foreign key at once. Used as a subject (?iri in the customer mapping) it identifies the row. Used as an object (?loc_iri) it points at another row. location:{location} in the customer mapping and location:{id} in the address mapping produce the same string for the same UUID: the matching names are the join.
  2. Stardog can read a template backwards. Ask about <urn:stardog:demos:c360:customer:225>. The slow way would be to fetch all 500 customer rows, build a name for each (…customer:1 … …customer:500) and compare every one with yours. Instead, Stardog knows the template is …customer:{cid}, removes the fixed part, is left with 225, and sends Aurora SELECT … FROM c360.customer WHERE cid = 225: one row, using the database's index.
  3. Values are percent-encoded. By default (percent.encode=true) illegal IRI characters such as spaces are escaped: "Acme Sports" becomes …vendor:Acme%20Sports (Chapter 9's vendor mapping).

These are the exact IRIs the original c360 kit used, so anything written against the kit keeps working. And the Redshift mapping will mint the same customer IRI from purchase.cid; Chapter 9 is built on that fact.

The IRI template is a computed natural key: a value object that turns the key into a name and parses the name back into the key, which is what lets Stardog push WHERE cid = 225 into the SQL.

SMS2

# subject: a global name built from the key
BIND(TEMPLATE(
  "urn:stardog:demos:c360:customer:{cid}")
  AS ?iri)

# object: the same kind of template
# in another row is a foreign key
BIND(TEMPLATE(
  "urn:stardog:demos:c360:location:{location}")
  AS ?loc_iri)

Java 21

record CustomerId(int cid) {
    static final String PREFIX =
        "urn:stardog:demos:c360:customer:";

    String iri() { return PREFIX + cid; }       // key -> name

    static CustomerId parse(String iri) {       // name -> key
        return new CustomerId(
            Integer.parseInt(iri.substring(PREFIX.length())));
    }
}

boolean same = new CustomerId(225)
    .equals(new CustomerId(225));     // true

Where the analogy breaks: a JPA @Id is unique only inside one table of one database; matching customers across two databases is code you write. An IRI is a global name: when the Aurora and Redshift mappings mint the same string, the two sides are the same node.

A template is a naming convention enforced by code. Two teams who never talk can make their data join if they agree on one string pattern for "a customer": the blog's "cooperation without coordination".

8.6The other Aurora mappings: address, card, rewards

The rest of aurora_c360_safe.sms uses the same four parts; each block adds one idea.

Address: computed values belong in the SQL

MAPPING <urn:c360:aurora:address>
FROM SQL {
  SELECT id, city, state, zip,
         street_number || ' ' || street_name || ' ' || street_suffix AS street_addr,
         street_number || ' ' || street_name || ', ' || state       AS label
  FROM c360.address
}
TO {
  ?iri a :Address ; :city ?city ; :streetAddress ?street_addr ; :zipCode ?zip ; :state ?state ; rdfs:label ?label .
}
WHERE { BIND(TEMPLATE("urn:stardog:demos:c360:location:{id}") AS ?iri) }

The ontology has one :streetAddress; the table has three street columns. Since BIND can't concatenate for SQL sources, the SELECT does it and the alias becomes a variable. The subject template, location:{id}, is where the customer's :address arrow lands.

Card: expose the fact, not the number

MAPPING <urn:c360:aurora:card>
FROM SQL { SELECT id, cid, card_type, card_type || ' ' || right(card_num, 4) AS label FROM c360.credit_card }
TO { ?cc a :CreditCard ; rdfs:label ?label ; :cardType ?card_type ; :cardHolder ?cust_iri . }
WHERE {
  BIND(TEMPLATE("urn:stardog:demos:c360:cards:{id}") AS ?cc)
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?cust_iri)
}

The safe graph knows a card's type and holder, and labels it with the type and last four digits (the usual "safe to display" convention). The full card_num is never exposed as a column, so no triple can carry it.

Rewards: an arrow in the other direction, and a cast

MAPPING <urn:c360:aurora:rewards>
FROM SQL { SELECT id, cid, account_id, create_date FROM c360.rewards_account }
TO {
  ?r a :RewardsAccount ; :openDate ?open_dt ; :accountId ?account_id ; rdfs:label ?account_id .
  ?cust :hasRewards ?r .
}
WHERE {
  BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?cust)
  BIND(TEMPLATE("urn:stardog:demos:c360:rewards:{id}") AS ?r)
  BIND(xsd:date(?create_date) AS ?open_dt)
}

Two new ideas. The TO block has two subjects: the row describes the account and emits ?cust :hasRewards ?r with the customer as subject. The foreign key lives on the rewards table, but the ontology's arrow points from customer to account (Chapter 6), and a mapping may emit arrows in whichever direction the ontology wants. And xsd:date(?create_date) is a cast: it types the literal as xsd:date, so date comparisons and YEAR() work (Chapter 3).

Only templates and casts in BIND. Port a CSV mapping (like the original kit's customers.sms, with BIND(CONCAT(?first_name, " ", ?last_name) AS ?label)) to a SQL source and those functions fail: CSV sources support all SPARQL functions, SQL sources only templates and casts. Move the expression into the SELECT as an aliased column.

8.7Safe and PII: why two graphs

Aurora holds two things marketing should never see: SSNs and full card numbers. Rather than hide them later, the build splits Aurora into two virtual graphs over the same data source:

  • aurora_c360_safe: customers, addresses, cards (type and last four only), rewards accounts. Everything you've seen so far.
  • aurora_c360_pii: only the two sensitive properties, :ssn and :cardNumber.

Here is the whole PII mapping. It's short on purpose:

# Virtual graph: aurora_c360_pii — ONLY the sensitive properties. Grant to hr_user, not marketing_user.
prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#>
prefix xsd: <http://www.w3.org/2001/XMLSchema#>
prefix : <tag:stardog:api:ecomm:>

MAPPING <urn:c360:aurora:pii:ssn>
FROM SQL { SELECT cid, ssn FROM c360.customer }
TO { ?iri :ssn ?ssn . }
WHERE { BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?iri) }
;
MAPPING <urn:c360:aurora:pii:card>
FROM SQL { SELECT id, card_num FROM c360.credit_card }
TO { ?cc :cardNumber ?card_num . }
WHERE { BIND(TEMPLATE("urn:stardog:demos:c360:cards:{id}") AS ?cc) }

The PII graph declares no types, names or addresses; it only adds facts to IRIs the safe graph describes, using the same templates. Read both graphs and you see one customer with an SSN; read only the safe graph and the SSN doesn't exist.

The safe/PII split is two projections of one table, like two DTOs over c360.customer, where only some callers get the second.

SMS2 + SPARQL

# aurora_c360_safe
TO { ?iri a :Customer ; :name ?full_name . }

# aurora_c360_pii: same template, same IRI
TO { ?iri :ssn ?ssn . }

# a user allowed to read both
# sees one customer, no merge step:
?c :name ?n ; :ssn ?s .

Java 21

// two projections of the same table
record CustomerSafe(int cid, String fullName) {}
record CustomerPii(int cid, String ssn) {}

List<CustomerSafe> safe = jdbc.query(
    "SELECT cid, full_name FROM c360.customer",
    (rs, i) -> new CustomerSafe(rs.getInt(1), rs.getString(2)));

// HR has to merge them by hand, on cid:
Map<Integer, String> ssnByCid = pii.stream()
    .collect(Collectors.toMap(CustomerPii::cid,
                              CustomerPii::ssn));

Where the analogy breaks: a DTO protects by convention (any code with the repository can still select ssn), and merging is code you write. Stardog enforces the split with per-graph permissions (Chapter 12), and for someone allowed both, the graphs combine automatically on shared IRIs.

The payoff comes in Chapter 12: named-graph security grants read access per graph, so marketing_user gets virtual://aurora_c360_safe only and hr_user gets both. (Chapter 12 also compares a property-level alternative, sensitive properties with masking.)

It's the same move as putting PII in a separate schema with its own grants rather than column-level grants on a wide table, except the source database doesn't change at all: the split exists only in the mappings.

The blog's mapping section makes this chapter's two points: mappings connect ontology terms to tables without moving data, and an IRI template such as urn:stardog:demos:c360:customer:{cid} gives each customer one identity across sources. Our safe/PII split sets up its hr_user vs marketing_user security demo.

Check yourself

What are the four parts of an SMS2 mapping block, and what does each do?

MAPPING names the block; FROM SQL is the source query whose columns become variables; TO lists the triple patterns emitted per row; WHERE binds new variables with TEMPLATE (IRIs) and casts (typed literals). Blocks are separated by semicolons after a prefix prologue.

How does the location column in customer become an arrow to an address node?

The customer mapping builds ?loc_iri with TEMPLATE("urn:stardog:demos:c360:location:{location}") and emits ?iri :address ?loc_iri. The address mapping mints its subjects with the same template from address.id. Same value, same template, same IRI: no join condition needed.

Why does the address mapping concatenate the street in SQL instead of using CONCAT in a BIND?

For SQL sources, BIND in SMS2 supports only TEMPLATE, datatype casts and strdt. Any other computation has to be done in the SELECT and exposed as an aliased column.

The rewards table has the cid column, yet the mapping emits ?cust :hasRewards ?r with the customer as subject. Why is that allowed?

A mapping can emit triples with any subject it can build. Direction follows the ontology (:hasRewards goes from customer to account), not which table holds the foreign key.

Why split Aurora into a safe graph and a PII graph instead of one graph?

Stardog's named-graph security grants read access per graph, so a sensitivity split at mapping time makes "marketing can't see SSNs" a single grant (Chapter 12). Because both graphs use the same IRI templates, anyone allowed to read both sees one customer node with all properties.

What would happen if the PII mapping used urn:c360:person:{cid} instead of urn:stardog:demos:c360:customer:{cid}?

It would produce SSN triples on different subjects, so step 6's query would return nothing: no IRI would have both a :name and an :ssn. Matching templates are the whole mechanism.

Chapter recap

  • A mapping says "run this SQL, emit these triples per row". For a virtual graph it's used backwards at query time to generate SQL.
  • SMS2 (Stardog's syntax, CONSTRUCT-like) is what we use; R2RML is the verbose W3C standard. Virtual graph option: mappings.syntax=SMS2.
  • Block anatomy: MAPPING name, FROM SQL, TO triples, WHERE binds. For SQL sources, BIND allows only templates and casts; compute everything else in the SQL.
  • IRI templates turn local keys into global names, act as primary and foreign keys at once, and let Stardog push key lookups into SQL.
  • We split Aurora into aurora_c360_safe and aurora_c360_pii over one data source; shared templates rejoin them for anyone allowed to read both.
