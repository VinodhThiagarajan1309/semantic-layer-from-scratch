Chapter 2

The triple: the atom of knowledge

Everything Stardog knows is a three-part sentence. By the end of this chapter you'll read, write and query them.

A riddle to start. How many columns does a table need to hold every fact your company knows: every customer's email, every order's price, which address belongs to whom, which product is in which category? Your Aurora and Redshift schemas use about fifty columns across eight tables; a real company has thousands. The answer is three: subject, predicate, object. That's the entire data model of this book's world, and once you read those three-part sentences fluently, the rest is mostly vocabulary. We'll start with Carolyn Inworth of Milwaukee, customer 225.

2.1One shape for everything

Stardog stores data using RDF, the Resource Description Framework, a W3C standard. RDF is to Stardog what the relational model is to Postgres. Its central idea fits on one line: every fact is a triple.

subject  →  predicate  →  object

Read one aloud and it's a plain English sentence. Customer 225 has first name "Carolyn". Order 0e7e… was purchased by customer 225. Here are the terms, each with what it is, why it exists, and a tiny example:

TermWhat it isWhy it existsTiny example
RDFA standard data model in which all information is triples.One shape for all data, so data from anywhere combines without reconciling schemas.The six facts you'll write in Section 2.6.
TripleOne fact: subject, predicate, object.The smallest unit you can add, delete, query or secure.customer:225 email "cinworth68@g.co"
SubjectThe thing the fact is about.Every fact needs an anchor.customer:225
PredicateThe property or relationship being stated.Names what kind of fact this is, like a column name, but global.firstName, purchasedBy
ObjectThe value, or the other thing at the end of the relationship.The fact's content."Carolyn", or customer:225
GraphA set of triples.It's what a database holds; drawn out, it's literally a network (Section 2.4).Everything in kit-c360.

No tables, no columns, no rows, no NULLs. Just a set of sentences.

Picture one table, triples(subject, predicate, object), holding every fact in the database, one fact per row. A SPARQL query is essentially a set of self-joins on this table (Chapter 4).

Where it breaks: Stardog doesn't physically store one big table (it keeps several indexes so any position can be looked up fast); the "object" column has no single type; and it's a set, so stating the same fact twice still gives one fact.

If you think in objects, a triple is one field assignment on one object:

RDF

customer:225  :firstName  "Carolyn" .
customer:225  :lastName   "Inworth" .
customer:225  :email      "cinworth68@g.co" .
# a second email, if she had one:
customer:225  :email      "c.inworth@example.com" .

Java

Customer carolyn = new Customer(225);
carolyn.firstName = "Carolyn";
carolyn.lastName  = "Inworth";
carolyn.email     = "cinworth68@g.co";
// a second email? Change the class:
// List<String> emails

Where the analogy breaks: no class has to exist first, any subject can take any predicate, and many values for one predicate are normal. The "field name" is global: :email means the same thing on a customer, a vendor or anything else.

2.2A SQL row becomes triples

Here's a real row from your Aurora database. Find it in DBeaver with SELECT * FROM c360.customer WHERE cid = 225, and its address with SELECT * FROM c360.address WHERE id = 'b80ea2ce-2361-408a-b443-721594cbbb35'. Press Play to watch them turn into triples.

Three rules did all the work, the same rules the mappings in Chapter 8 follow:

  1. The primary key becomes the subject's name. Every triple from the row is about customer 225. The key isn't a triple of its own; it's baked into the name, customer:225 (Chapter 3 gives the full-length names).
  2. Each ordinary column becomes one triple. first_name = 'Carolyn' becomes customer:225 firstName "Carolyn".
  3. A foreign key becomes an arrow to another thing. location holds a reference, not a value you'd show anyone. So the object is the address itself, location:b80e…, which then has its own triples.

Two more things startle SQL people. NULL disappears. Carolyn's picture column is empty, so there's simply no picture triple: the fact is absent. (That's the seed of the open-world assumption, Chapter 5.) And multiple values are free. Two emails are two email triples: no email2 column, no child table, no schema change.

Three table shapes you know, and what each becomes. (Examples marked hypothetical use a table our c360 data doesn't have; everything else is real.)

1. A child table for a multi-valued column becomes several triples with the same predicate. Hypothetical table customer_email:

cidemail
225cinworth68@g.co
225carolyn@work.example

becomes two triples, and there is no second table:

customer:225  :email  "cinworth68@g.co" .
customer:225  :email  "carolyn@work.example" .

2. A join table for a many-to-many becomes one triple per row. Hypothetical table product_category, if a product could sit in several categories (the Tent, product 34, is really in Outdoors, category 14):

product_idcategory_id
34 (Tent)14 (Outdoors)
34 (Tent)10 (Sports)

becomes two triples. The join table itself disappears:

product:34  :inCategory  category:14 .
product:34  :inCategory  category:10 .

3. A join table whose rows carry their own columns becomes a thing of its own. The real purchase table links a customer to a product, but each row also has a date, a quantity and a price. Those extra columns need somewhere to hang, so the row becomes an Order with its own name. Carolyn's real purchase of Wax Paper:

idcidpiddatequantityprice
363f9784-…225268 (Wax Paper)2013-04-182110479.00

becomes a new thing, purchase:us:pos363f9784-…, with six triples:

purchase:us:pos363f9784-…  a               :Order .
purchase:us:pos363f9784-…  :purchasedBy    customer:225 .
purchase:us:pos363f9784-…  :itemPurchased  product:268 .
purchase:us:pos363f9784-…  :purchaseDate   "2013-04-18" .
purchase:us:pos363f9784-…  :quantity       21 .
purchase:us:pos363f9784-…  :purchasePrice  10479.00 .

The rule of thumb: if the link is just "A relates to B", it's one triple. If the link has facts of its own (when, how many, how much), it becomes a thing.

2.3Things and literals

Figure 2.1 draws its objects in two shapes on purpose, and the distinction matters early:

TermWhat it isWhy it existsTiny example
IRIA globally unique name, written like a URL or URN, in angle brackets.So a thing or property means the same everywhere, even when data from different systems is mixed (Chapter 3).<urn:stardog:demos:c360:customer:225>
Resource (a "thing")Anything named by an IRI: a customer, an address, a property.Things can have their own facts: arrows can start from them.The address node, which has a city and a state.
LiteralA plain value: text, number, date. Always an object, never a subject.Facts eventually bottom out in values you display, filter and add up."Milwaukee", 22, 439.78

Why is the address a thing but the city a literal? Because the address has facts of its own and, in our model, the city doesn't. You decide it the way you decide whether something deserves its own table: if it has attributes, or other things point to it, make it a thing. To record Milwaukee's population, you'd promote the city to a thing (city:milwaukee-wi) and hang facts off it.

A string that looks like a name is still just a string. "urn:stardog:demos:c360:customer:225" in quotes is a literal, not a reference to Carolyn, and nothing connects to it. Things go in angle brackets <…>, literals in quotes "…"; mixing them up is the most common beginner mistake, and it fails silently with zero results.

2.4The graph as a picture, and why merging is free

Figure 2.1's bottom half isn't an illustration of the data. It is the data. Subjects and objects are nodes; each triple is an edge labeled with its predicate. That's why the whole field is called knowledge graphs.

This matters enormously in Chapter 9. Because every triple has the same shape, two sets of triples combine by simply pouring them together, with no schemas to reconcile. Where both sets use the same name for the same thing, the pictures join up at that node by themselves.

Here's a real order from Redshift (SELECT * FROM c360.purchase WHERE id = '0e7edc35-b578-44a0-a58c-e6388bc83337'): on 2011-01-21, customer 225 bought 22 of product 258 ("Flip Flops" by Havaianas, in c360.product) for $439.78. Pour its triples next to Carolyn's:

Nobody wrote a JOIN. The order's purchasedBy arrow points at customer:225, and the Aurora triples are about a node with exactly the same name. That's the whole secret of the federated join, and why Chapter 3 spends so long on how names are built.

Tables are jigsaw pieces: each fits only the pieces it was cut for. Triples are Lego bricks with one universal connector: any set fits with any other, and where two sets mention the same named thing, they lock together.

2.5Follow the arrow instead of writing a JOIN

"Which city does customer 225 live in?" You could write the SQL in your sleep:

SELECT a.city
FROM c360.customer c
JOIN c360.address  a ON a.id = c.location
WHERE c.cid = 225;

In a graph you describe the path through the picture, with blanks where you want answers. The language is SPARQL (Chapter 4); for now just read the shape (the runnable version is in the Try it box):

SELECT ?city
WHERE {
  customer:225  address  ?home .
  ?home         city     ?city .
}
TermWhat it isWhy it existsTiny example
SPARQLThe W3C query language for RDF (say "sparkle").SQL assumes tables; triples need a language built around patterns and paths.The query above.
Triple patternA triple where some positions are variables (placeholders) instead of fixed values.You describe the shape of the facts you want; Stardog finds every triple that fits.?home :city ?city . matches location:b80ea2ce… :city "Milwaukee", giving ?home = location:b80ea2ce…, ?city = "Milwaukee"
VariableA placeholder name, starting with ?, for a value you don't know yet. Stardog fills it in from the matching triples, and each variable becomes a column in your results.Marks what you want back, and links lines together: the same name on two lines must be the same value (like a JOIN condition).customer:225 :address ?home .
?home :city ?city .
→ ?home = location:b80ea2ce…, ?city = "Milwaukee"

To be honest about what's underneath: Stardog is still joining, on ?home, much like a self-join on the imaginary three-column table. What changes is what you need to know to write the query: not table names or foreign keys, just the names of the relationships, address then city. The "how do these connect" knowledge has moved out of every query and into the data.

Following arrows is navigating object references:

SPARQL

customer:225  :address  ?home .
?home         :city     ?city .

# backwards: who lives in Milwaukee?
?who   :address  ?home .
?home  :city     "Milwaukee" .

Java

String city = carolyn.getAddress().getCity();

// backwards? There's no getResidents()
// on Address. You'd loop over every
// Customer, or add a reverse reference.

Where the analogy breaks: Java can only walk references a class declared, and only forward. A graph pattern can start anywhere and go either way. And a missing address simply gives no row, not a NullPointerException.

Two more gifts. Arrows can be followed backwards, as the Java box shows: just move the variable. And paths across sources look like paths within one: in Figure 2.2, going from an order to its customer's state is purchasedBy, address, state, even though the first arrow comes from Redshift and the rest from Aurora. The query doesn't care where triples live.

In the blog, this chapter sits underneath the mappings and IRI template section. The blog's mappings present Aurora and Redshift rows as exactly the triples you'll write by hand below, with subjects named from row keys (urn:stardog:demos:c360:customer:{cid}). Writing six by hand first makes that section read as obvious rather than magical.

2.6Hands-on: six triples about Carolyn

Your turn. You'll put the six triples from Figure 2.1 into a scratch folder, query them three ways, and delete the folder. Three new terms first:

TermWhat it isWhy it existsTiny example
Named graphA set of triples with its own IRI as a label; a folder inside the database (Chapter 3).To keep groups of triples separate: to query, secure or delete them as a unit.<urn:book:ch02>
INSERT DATAA SPARQL command that adds exactly the triples you list.The simplest way to write facts by hand.Step 1 below.
DROP GRAPHA SPARQL command that deletes a named graph and every triple in it.One-line cleanup, like DROP TABLE.DROP GRAPH <urn:book:ch02>

The names are long: <urn:stardog:demos:c360:customer:225> for Carolyn, <tag:stardog:api:ecomm:firstName> for "first name". Chapter 3 explains how to build and shorten them. For today, read <…customer:225> as "customer 225" and <…ecomm:firstName> as "first name".

Where: Stardog Studio, Workspace. Choose the database kit-c360 at the top. If there's a reasoning toggle, leave it off. Paste each block and click Run (or press ⌘+Enter). If anything on screen doesn't match, send Claude a screenshot.

Step 1. Write six triples. Each line is subject, predicate, object, then a full stop. GRAPH <urn:book:ch02> { … } says which folder.

INSERT DATA {
  GRAPH <urn:book:ch02> {
    <urn:stardog:demos:c360:customer:225>  <tag:stardog:api:ecomm:firstName>  "Carolyn" .
    <urn:stardog:demos:c360:customer:225>  <tag:stardog:api:ecomm:lastName>   "Inworth" .
    <urn:stardog:demos:c360:customer:225>  <tag:stardog:api:ecomm:email>      "cinworth68@g.co" .
    <urn:stardog:demos:c360:customer:225>  <tag:stardog:api:ecomm:address>    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35> .
    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35>  <tag:stardog:api:ecomm:city>   "Milwaukee" .
    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35>  <tag:stardog:api:ecomm:state>  "Wisconsin" .
  }
}

Expect: a success message and no result table. Notice line four: its object is in angle brackets, so it's a thing (the address), not a literal.

Why some names start with urn: and others with tag:? Everything in angle brackets is an IRI, so everything in angle brackets is a thing, including firstName. The urn: or tag: at the front is just a naming format, like https: or mailto:; it doesn't tell you what role the thing plays. The role comes from where it sits in the triple: first position = subject, middle = predicate, last = object. The c360 kit's authors happened to name data items (customer 225, her location) urn:stardog:demos:c360:… and vocabulary (firstName, city) tag:stardog:api:ecomm:…; they could have used https: for all of it. Because a predicate is a thing too, it can have facts of its own: in Chapter 6, firstName moves to the subject position in <tag:stardog:api:ecomm:firstName> rdfs:label "first name". Only quoted literals like "Carolyn" can never be a subject. Chapter 3 covers IRIs in full.

Step 2. Read everything back. One pattern, three blanks: "every triple in the folder".

SELECT ?s ?p ?o
WHERE { GRAPH <urn:book:ch02> { ?s ?p ?o } }

Expect 6 rows, in no particular order: four with the customer as s, two with the location.

Step 3. Say it twice. Run the Step 1 block again, unchanged, then Step 2 again. Expect: still 6 rows. A graph is a set; restating a fact changes nothing. (A SQL table without a primary key would now have duplicates.)

Step 4. Follow the arrows. "Which city does customer 225 live in?"

SELECT ?city
WHERE {
  GRAPH <urn:book:ch02> {
    <urn:stardog:demos:c360:customer:225>  <tag:stardog:api:ecomm:address>  ?home .
    ?home  <tag:stardog:api:ecomm:city>  ?city .
  }
}

Expect one row: "Milwaukee".

Step 5. Follow them backwards. "Who lives in Wisconsin, and what's their first name?"

SELECT ?who ?first
WHERE {
  GRAPH <urn:book:ch02> {
    ?who   <tag:stardog:api:ecomm:address>    ?home .
    ?home  <tag:stardog:api:ecomm:state>      "Wisconsin" .
    ?who   <tag:stardog:api:ecomm:firstName>  ?first .
  }
}

Expect one row: urn:stardog:demos:c360:customer:225, "Carolyn". Now change "Wisconsin" to "wisconsin" and run again: 0 rows. Literals match exactly, like a case-sensitive =.

Step 6. Clean up.

DROP GRAPH <urn:book:ch02>

Step 7. Verify it's empty.

SELECT (COUNT(*) AS ?n)
WHERE { GRAPH <urn:book:ch02> { ?s ?p ?o } }

Expect one row: n = 0.

Run DROP GRAPH <urn:book:ch02> a second time and, since the graph no longer exists, you may see an error. Harmless. DROP SILENT GRAPH <urn:book:ch02> means "drop it if it's there, and don't complain otherwise", handy at the top of a script you might rerun.

Notice what you never said. You never told Stardog that customer 225 is a Customer or that "firstName" is something customers have. There was no CREATE TABLE; Stardog accepted your sentences without knowing what any word means. That missing vocabulary is the T-Box (the schema), which Chapters 5 and 6 build. Your six facts about one customer are A-Box (the data).

Check yourself

A SQL row has six non-null columns, including the primary key. About how many triples does it become?

About five, one per non-key column. The primary key becomes part of the subject's name (customer:225) rather than a triple. NULL columns produce nothing.

Is "Milwaukee" a thing or a literal in our model? Why?

A literal: a plain text value in quotes, with no arrows leaving it. To state facts about the city itself, you'd make it a thing with its own IRI.

Why is the address a thing and not a literal?

It has facts of its own (city, state, zip), and only things can be subjects. It also started as a foreign-key target, which is the usual sign.

You run the same INSERT DATA twice. How many triples are there?

The same as after the first run. A graph is a set; restating a triple changes nothing.

In the "which city" query, what plays the role of the JOIN condition?

The shared variable ?home: it's the object of the first pattern and the subject of the second, so both must match the same node. You express the join by naming relationships, not matching key columns.

Why do the Aurora and Redshift triples in Figure 2.2 connect without any join logic?

Both use exactly the same name for customer 225, and triples naming the same thing are about the same node. Building those names consistently from cid is the IRI trick of Chapters 3 and 9.

Chapter recap

  • RDF stores every fact as a triple: subject predicate object. A set of triples is a graph.
  • A SQL row becomes triples: key → subject name, column → one triple, foreign key → arrow to another thing, NULL → nothing.
  • Objects are either things (named by IRIs, can have their own arrows) or literals (plain values, dead ends).
  • Triples from different sources combine by simple union and connect wherever they use the same name.
  • A SPARQL query is a pattern of triples with variables; a shared variable does the job of a join key, in either direction.
  • You wrote, queried and deleted six triples in <urn:book:ch02>: your first A-Box, with no T-Box yet.
