Chapter 5

The T-Box, part 1: classes (RDFS)

Where a graph keeps its schema, what a "class" really is, and why that schema describes your data instead of policing it. Then you write the first real piece of the c360 model.

Imagine inserting one triple saying that Carolyn Inworth's shoe size is 38. There is no shoe-size property anywhere, no class that mentions shoes, no schema at all. Stardog says "OK" and stores it. Try that in Aurora (UPDATE customer SET shoe_size = 38 WHERE cid = 225) and Postgres stops you cold: column does not exist. Your instinct says the graph is being sloppy. By the end of this chapter you will see that it is deliberate, that this choice is what makes a semantic layer over many databases possible, and where to go when you do want the database-style "no". Along the way you will write the first ten classes of the real c360 model: build step 1.

5.1Schema and data: the T-Box and the A-Box

So far every triple you have written was about one particular thing: Carolyn's email, the price of one order. Knowledge-graph people split triples into two families:

  • The T-Box ("terminology box") holds triples about kinds of things: "there is a class called Customer", "an Order is purchased by a Customer". It is the schema.
  • The A-Box ("assertion box") holds triples about particular things: "customer 225 is a Customer", "customer 225's first name is Carolyn". It is the data.

Why new names for "schema" and "rows"? Because in a graph they are made of the same stuff: both are triples, both sit in named graphs, both are queried with the same SPARQL. The names say which role a triple plays. The whole T-Box for a domain is an ontology (Stardog's tools also call it a model): one shared, machine-readable vocabulary for an organization. The single triple :Customer a owl:Class is already a very small ontology. Chapters 2 to 4 were A-Box work; this chapter and the next are T-Box work.

The T-Box and A-Box split is the split between a class and its objects: the declaration you compile versus the instances on the heap.

RDF / OWL (Turtle)

# T-Box: the schema
:Customer a owl:Class ;
    rdfs:label "Customer" .

# A-Box: the data
customer:225 a :Customer ;
    :firstName "Carolyn" .

Java 21

// "T-Box": the type, fixed at compile time
public class Customer {
    String firstName;
}

// "A-Box": an instance, on the heap at runtime
var c225 = new Customer();
c225.firstName = "Carolyn";

Where the analogy breaks: in Java you need reflection to look at a class as data. In RDF both are plain triples in the same store: SELECT ?c WHERE { ?c a owl:Class } is an ordinary query, and the schema is loaded, versioned and permissioned like any other graph.

The T-Box is your DDL plus the data dictionary (CREATE TABLE, COMMENT ON TABLE); the A-Box is the rows. Two differences matter. DDL lives in a special catalog (information_schema); the T-Box is ordinary triples, queried with Chapter 4's SPARQL. And DDL is a gatekeeper that rejects rows that do not fit. The T-Box is not: that is Section 5.5, the heart of this chapter.

5.2RDFS and OWL: why there are two schema languages

RDFS (RDF Schema, prefix rdfs: = http://www.w3.org/2000/01/rdf-schema#) came first (W3C, 1999 to 2004), because plain RDF can state facts but cannot say what kinds of things exist. It adds the bare minimum: classes, subclasses, labels, comments, and a way to say which classes a property connects. Tiny example: :Customer a rdfs:Class ; rdfs:label "Customer" .

OWL (the Web Ontology Language, prefix owl: = http://www.w3.org/2002/07/owl#; the letters are deliberately shuffled) followed in 2004, with OWL 2 in 2009. OWL is built on top of RDFS: everything RDFS says still holds, and OWL adds more precise statements. Three of them, each with our data (the property :placedOrder and the CRM name are hypothetical; the rest is real):

OWL can say…Written asWhat you gain
1. This link is the reverse of that one.
"Order → purchased by → Customer" and "Customer → placed order → Order" are the same fact read from opposite ends.		 :placedOrder owl:inverseOf :purchasedBy . You store only order:363f9784… :purchasedBy customer:225. Ask for customer:225 :placedOrder ?o and Stardog answers order:363f9784… (Carolyn's Wax Paper order), although that triple was never stored.
2. These two kinds can never overlap.
Nothing can be both a Customer and a Product.		 :Customer owl:disjointWith :Product . If a bad mapping ever produces customer:225 a :Product, a reasoner reports it as a contradiction (Carolyn can't be a product) instead of silently mixing customers into product lists.
3. These two names are the same thing.
A CRM calls Carolyn crm:person:C-0225; we call her customer:225.		 customer:225 owl:sameAs crm:person:C-0225 . Facts about either name now count for both: the CRM's loyalty tier and our purchases come back together when you ask about Carolyn.

RDFS alone can say none of these three things. It knows that a Customer is a kind of thing and that one kind sits under another, but not reverses, exclusions or aliases. The tiny example :Customer a owl:Class . declares a class exactly as rdfs:Class does; for this book the two are interchangeable. The difference is in the extra statements OWL makes possible, like the three above.

RDFS is the foundation, OWL the extension, and real ontologies mix both. The c360 kit declares classes with owl:Class (every OWL class is also an RDFS class) and labels them with rdfs:label. Chapter 6 ends with a one-page comparison once you have seen properties too.

5.3Classes and rdf:type

A class is a named set of things: all customers, all orders. You declare one by giving its IRI a type of its own, and connect a thing to it with rdf:type, the predicate you have been typing as a since Chapter 3:

:Customer a owl:Class .                            # T-Box: Customer is a class
<urn:stardog:demos:c360:customer:225> a :Customer .   # A-Box: 225 is a Customer

The class declaration has no column list. A class does not own properties the way a table owns columns; properties are declared separately and point at classes (Chapter 6). And because rdf:type is just a triple, you get freedoms a table never gives you:

  • A thing can have several types. In Chapter 10 Carolyn will be both :Customer and :Big_Spender, and nobody will have stored the second one.
  • A thing can have no type at all. Chapter 4's Queries 3 and 5 would have worked even without the a :Customer triples, because they only followed properties.
  • Types can be added later, by anyone, in any graph, with no ALTER TABLE.

By convention class names are capitalized (:CreditCard) and properties are not (:firstName). Nothing enforces it; everyone relies on it.

rdf:type reads like instanceof, and ASK { customer:225 a :Customer } behaves like it. Everything around that check differs.

RDF / SPARQL

customer:225 a :Customer .
# later, from another graph or a rule:
customer:225 a :Big_Spender .

# no type at all is also fine:
product:7 :name "Tent" .

ASK { customer:225 a :Customer }   # true

Java 21

Object c = new Customer();
boolean yes = c instanceof Customer;   // true

// One object, one class, chosen at `new`
// and fixed for its whole life.
// There is no:
//   c.addType(BigSpender.class);
// and no object without a class.

Where the analogy breaks: a node can have many types, gain them later, or have none. Nothing is "created as" a Customer; the type is one more fact about it, and an owl:Class has no fields. The nearest Java idea is a Set<String> tags that anyone may add to, not a class.

Now the labels. rdfs:label gives a human-readable name ("Credit Card") and rdfs:comment a description (the kit's "A concept representing a Customer's rewards account."). They look like decoration but are load-bearing: when Voicebox (Chapter 13) or your agent (Chapter 14) turns "Who are our top spenders in Wisconsin?" into SPARQL, labels and comments are much of what the language model reads to decide which class "spenders" means.

5.4Subclasses: inheritance you get for free

rdfs:subClassOf says every member of one class is also a member of another. This triple is real; it is in the kit's extended model, which you load in Chapter 10:

:Big_Spender rdfs:subClassOf :Customer .

The pay-off is inference: a new fact concluded from existing ones. Given customer:225 a :Big_Spender, a reasoner concludes customer:225 a :Customer, although nobody stored it.

rdfs:subClassOf is closer to implements than extends: a class may have several parents, and only membership is inherited.

RDFS

:Big_Spender rdfs:subClassOf :Customer .
# a second parent is legal
# (hypothetical, not in the kit):
:Big_Spender rdfs:subClassOf :VipContact .

customer:225 a :Big_Spender .
# with reasoning ON, 225 now matches:
SELECT ?c WHERE { ?c a :Customer }

Java 21

interface Customer {}
interface VipContact {}
interface BigSpender extends Customer, VipContact {}

record Carolyn() implements BigSpender {}

Object c = new Carolyn();
boolean yes = c instanceof Customer;  // true

Where the analogy breaks: Java checks the hierarchy at compile time and always; RDF applies it only when a reasoner is on (with the toggle off, the query above does not return 225). And anyone can add a subClassOf triple later to classes they did not write, like retroactively making String implement your interface.

The closest SQL picture is a view: CREATE VIEW all_customers AS SELECT cid FROM customer UNION SELECT cid FROM big_spender. A reasoner gives you that union for every class, in every query, from one subClassOf triple. Unlike PostgreSQL's INHERITS, it is only about membership, not storage or columns.

Two practical notes. Inference happens only with Studio's reasoning toggle on, and it stays off until Chapter 10. And inferences are computed at query time, never written to disk, so they cannot go stale; that is why reasoning works over virtual graphs, whose data is not in Stardog at all. The base c360 schema has no subClassOf triples: ten flat classes cover the core questions, and the hierarchy arrives with the business rules in Chapter 10.

5.5The open-world assumption

Back to Carolyn's shoe size: this is the mindset shift of the book. Every database you have used runs on the closed-world assumption: the database is the complete record of its slice of the world. No order row for customer 225 in March means she ordered nothing in March; a bad foreign key is rejected at the door. Absence means "false", and the schema is a contract data must pass to get in.

RDFS and OWL run on the open-world assumption: a graph is what is known, never a claim to know everything. A missing triple means "not stated here", not "false". No phone triple for Marlane does not mean she has no phone (she has one; you left it out in Chapter 4).

There is no good Java analogy, and it is worth seeing why. Java is thoroughly closed-world: the compiler rejects an unknown field, and Optional.empty() is a deliberate "no value" set by whoever built the object.

RDF / SPARQL

# accepted: no class mentions :shoeSize
customer:225 :shoeSize 9 .

# Marlane has no :phone triple.
# That means "not stated here",
# not "Marlane has no phone".
ASK { customer:88 :phone ?p }   # false

Java 21

record Customer(String name, Optional<String> phone) {}

var c = new Customer("Marlane", Optional.empty());
// c.shoeSize = 9;   // compile error: no such field

// empty() was put there on purpose by the object's
// author, and it means "none":
boolean noPhone = c.phone().isEmpty();   // true

Where the analogy breaks: Java has no value for "unknown"; even a nullable Boolean lives inside an object one owner built completely. A graph has no owner and no complete object: facts about customer 88 arrive from Aurora, Redshift and rules. And RDFS/OWL are not a compiler; the nearest gatekeeper is SHACL (Chapter 11), run as an explicit step, like calling Bean Validation yourself.

Four consequences, from most to least surprising:

  1. The schema does not reject data. Nothing stops an undeclared property, a customer with three emails, or an order with no customer. RDFS and OWL have no NOT NULL, no CHECK, no foreign keys.
  2. Where SQL raises an error, a reasoner draws a conclusion. The reasoner fills gaps instead of refusing. Chapter 6 shows the famous case: tell it that only orders are "purchased by" someone, feed it a buggy triple, and it concludes that a box of Wax Paper is an order.
  3. Different names are not assumed to be different things. Two IRIs might name the same customer. Ours are built from the same keys on both sides (the "IRI trick", Chapter 9), so this rarely bites.
  4. Queries still answer from what is there. SPARQL evaluates patterns over the triples it has: FILTER NOT EXISTS { ?c :phone ?p } returns customers with no phone triple, a perfectly closed-world answer. The open world does not change how SPARQL runs; it changes how you read the result ("no phone triple in the graphs we queried") and what the reasoner may conclude. Recall Chapter 4's Query 5, where Marlane "outspent" Carolyn only because we loaded two orders each.

A database is a ledger: it claims to be complete and checks every entry at the door. A knowledge graph is a case file: it gathers what is known from many sources, expects gaps, and lets you reason with what you have. For the ledger's door check you add a separate tool: SHACL, in Chapter 11.

Why build it this way? Because the open world is the honest assumption when data comes from many places. Aurora does not "know" that a customer has no orders; orders are not its job. A closed-world schema over Aurora and Redshift would either reject good data or lie about completeness. A semantic layer describes data it does not own. The price: validation becomes a separate, explicit step.

Two habits to unlearn. "I declared the class, so bad data can't get in": declarations describe, they do not guard. "The query returned nothing, so the answer is no": maybe, or the fact lives in a graph you did not query. That distinction goes into your agent's instructions in Chapter 14.

5.6Where the c360 model lives

The model gets its own named graph, <urn:stardog:training-c360:1.0:model>, in the kit-c360 database (the name comes from the c360 knowledge kit; 1.0 is a version). A separate graph pays off three times: in Chapter 6 you register it as the reasoning schema; from Chapter 8 on the data stays in Aurora and Redshift, so this graph (plus Chapter 10's rules) is all that is physically stored in Stardog; and in Chapter 12 named graphs are the unit of permission, so everyone can read the model even when they cannot read the PII.

The AWS blog's ontology section calls the c360 model the "meaning" layer between the language model and the warehouses, and builds it visually in Stardog Designer, which produces exactly the triples you are about to type. The blog's "where to start" advice (pick one workflow, write three to five competency questions, then bootstrap the ontology) is the order this book follows: "Who are our top spenders in Wisconsin?" needs Customer, Address and Order, and the kit adds seven more classes around them.

5.7Real build step 1: the ten classes

This is not scratch work: these triples start the model the reasoner, Voicebox and your agent will use. They are word for word the class declarations in the kit's schema.ttl, so loading the full file in Chapter 6 creates nothing different.

Step 1: insert the classes. In Studio's Workspace, open a query tab on kit-c360, reasoning off, paste and run:

PREFIX :     <tag:stardog:api:ecomm:>
PREFIX owl:  <http://www.w3.org/2002/07/owl#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

INSERT DATA {
  GRAPH <urn:stardog:training-c360:1.0:model> {
    :Industry       a owl:Class ; rdfs:label "Industry" .
    :Vendor         a owl:Class ; rdfs:label "Vendor" .
    :Customer       a owl:Class ; rdfs:label "Customer" .
    :Address        a owl:Class ; rdfs:label "Address" .
    :Order          a owl:Class ; rdfs:label "Order" .
    :Product        a owl:Class ; rdfs:label "Product" .
    :Category       a owl:Class ; rdfs:label "Category" .
    :CreditCard     a owl:Class ; rdfs:label "Credit Card" .
    :UnitPrice      a owl:Class ; rdfs:label "Unit Price" .
    :RewardsAccount a owl:Class ;
        rdfs:comment "A concept representing a Customer's rewards account." ;
        rdfs:label   "Rewards Account" .
  }
}

That is 21 triples: ten a owl:Class, ten rdfs:label, one rdfs:comment. Running it twice is harmless; a graph is a set.

Step 2: count them. Expect 21.

SELECT (COUNT(*) AS ?triples)
WHERE {
  GRAPH <urn:stardog:training-c360:1.0:model> { ?s ?p ?o }
}

Step 3: list them. Expect 10 rows, sorted by label: Address, Category, Credit Card, Customer, Industry, Order, Product, Rewards Account, Unit Price, Vendor.

PREFIX owl:  <http://www.w3.org/2002/07/owl#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?class ?label
WHERE {
  GRAPH <urn:stardog:training-c360:1.0:model> {
    ?class a owl:Class ;
           rdfs:label ?label .
  }
}
ORDER BY ?label

Step 4: meet the open world. Ask whether the model graph says Carolyn is a customer:

PREFIX : <tag:stardog:api:ecomm:>

ASK {
  GRAPH <urn:stardog:training-c360:1.0:model> {
    <urn:stardog:demos:c360:customer:225> a :Customer
  }
}

Expect false, read as "this graph does not state it", not "Carolyn is not a customer". She arrives through the Aurora virtual graph in Chapter 8.

Do not drop this graph. It stays for the rest of the book.

A typo such as :Cusotmer is accepted without complaint. Fix it with a DELETE DATA of exactly the wrong triple in the same graph, then rerun Step 1. If the count is not 21 and you cannot see why, it is safe now (and only now, before Chapter 6) to run DROP GRAPH <urn:stardog:training-c360:1.0:model> and repeat Step 1. Mention it to Claude.

Check yourself

Which are T-Box and which A-Box: (a) :Order a owl:Class, (b) customer:225 :firstName "Carolyn", (c) customer:225 a :Customer, (d) :Big_Spender rdfs:subClassOf :Customer?

(a) and (d) are T-Box (kinds of things); (b) and (c) are A-Box (one customer). (c) is the bridge: an A-Box triple whose object is a T-Box class.

Why do both RDFS and OWL exist, and which does the c360 kit use?

RDFS is deliberately minimal (classes, subclasses, labels, domain/range). OWL builds on it to express inverse relationships, disjoint classes and identity. The kit uses both: owl:Class and OWL property types, with rdfs:label and rdfs:comment.

Someone inserts customer:999 :favoriteColor "teal", and no such property is declared. What happens?

Stardog stores it. Under the open world the model describes; it does not reject. To have such data reported, use SHACL (Chapter 11).

A query for customers without an email returns Marlane. What exactly may you conclude?

Only that no :email triple for her exists in the graphs you queried, not that she has no email. (In Aurora she has one.)

With reasoning on, why does ?c a :Customer return a thing whose only stored type is :Big_Spender?

Because :Big_Spender rdfs:subClassOf :Customer lets the reasoner infer the type at query time. The inferred triple is never written to disk.

Chapter recap

  • The T-Box (the ontology or model) describes kinds of things; the A-Box describes particular things. Both are ordinary triples.
  • RDFS is the minimal schema vocabulary; OWL builds on it with more precise tools. Real ontologies mix both.
  • A class is a named set; rdf:type (a) puts a thing in it. Things can have many types or none; classes have no columns.
  • Labels and comments are for people and AI, and here they are load-bearing.
  • rdfs:subClassOf lets a reasoner infer membership at query time, like an automatic UNION view that is never stored.
  • Open world: absent means "not stated here", and the schema describes rather than rejects. Validation is a separate tool (SHACL).
  • Build step 1 is done: 21 triples, 10 classes, in <urn:stardog:training-c360:1.0:model>. It stays.
