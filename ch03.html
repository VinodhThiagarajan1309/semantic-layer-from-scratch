Chapter 3

Names, values and files

How things get globally unique names, why every value carries a type, how triples are written to files, and where they're kept.

Carolyn Inworth has spent exactly $502,529.42 with us; Redshift says so, to the cent. Now write that number into a graph twice. Label it once as a decimal and once as a float, and read both back. The decimal returns $502,529.42. The float returns $502,529.40625. Same number, same database; the only difference is one word saying what type of value it is, and that one word puts one customer's total two cents off. This chapter is about the unglamorous things that decide whether a knowledge graph is right or almost right: how things are named, how values carry their types, how triples are written in files, and which folder they're kept in.

3.1Names that mean the same thing everywhere

In Aurora, 225 means Carolyn only because it sits in the cid column of c360.customer. In Redshift, product.id = 225 is a product. A key means something only together with its table.

A graph has no tables to supply that context, and triples from different sources mix freely (Figure 2.2). So every thing needs a name that means the same everywhere and can't collide. That's what IRIs are for:

TermWhat it isWhy it existsTiny example
IRI (Internationalized Resource Identifier)A globally unique name in URL/URN form. It needn't point anywhere; Stardog never fetches it.So a name means the same in any system.urn:stardog:demos:c360:customer:225
URNAn IRI scheme (urn:) for names that aren't web locations.Naming things without pretending they're web pages.Our data IRIs.
tag: IRIAn IRI scheme (RFC 4151) for minting unique names without registering anything.A cheap, collision-free vocabulary namespace.tag:stardog:api:ecomm:firstName
Namespace / local nameThe shared beginning of a family of IRIs / the part after it.Lets a prefix abbreviate the common part (Section 3.4).tag:stardog:api:ecomm: + firstName

One property of IRIs catches everyone: they're compared as exact strings. …customer:225, …Customer:225 and …customer:0225 are three different things. One stray character and you have a stranger.

An IRI is like a fully qualified primary key, c360.customer.225, except the qualification is part of the value and unique across every database on earth. Where the analogy breaks: a SQL key means nothing without its table, while an IRI can turn up in a triple from a completely different source and still refer to the same thing.

An IRI is like a fully qualified name, and a prefix is like an import:

RDF / SPARQL

PREFIX : <tag:stardog:api:ecomm:>

# full:  <tag:stardog:api:ecomm:Customer>
# short: :Customer

<urn:stardog:demos:c360:customer:225>

Java

import com.acme.ecomm.Customer;

// full:  com.acme.ecomm.Customer
// short: Customer

// an instance has no global name;
// new Customer(225) is just a reference

Where the analogy breaks: a Java FQN names classes; an IRI names everything, including individual objects like customer 225, whereas an object reference only means something inside one JVM. And a prefix is pure text substitution; nothing is loaded or checked.

3.2Names built from keys: a preview of the IRI trick

Nobody types urn:stardog:demos:c360:customer:225 by hand. It's computed from the row's key by an IRI template: a fixed string with a slot for a column, like urn:stardog:demos:c360:customer:{cid}, so the same row gets the same name every time, from any system (Chapter 8 writes them). Every c360 thing follows one pattern, urn:stardog:demos:c360:<kind>:<key>:

KindTemplate (after urn:stardog:demos:c360:)Key column(s)
Customercustomer:{cid}Aurora customer.cid, and Redshift purchase.cid
Addresslocation:{id}Aurora address.id (and customer.location)
Credit card · rewards accountcards:{id} · rewards:{id}Aurora credit_card.id · rewards_account.id
Orderpurchase:us:pos{id}Redshift purchase.id
Product · category · unit priceproduct:{id} · category:{id} · unitprice:{id}Redshift product.id, category.id
Vendor · industryvendor:{vendor_name} · industry:{industry}Redshift vendor columns

The customer template appears in both databases. Here's the actual line from the Aurora mapping (Chapter 8) and the Redshift mapping (Chapter 9):

# Aurora mapping, c360.customer
BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?iri)

# Redshift mapping, c360.purchase
BIND(TEMPLATE("urn:stardog:demos:c360:customer:{cid}") AS ?cust_iri)

Both sides produce exactly the same string for Carolyn, and triples that use the same name are about the same node (Section 2.4). The blog calls this the IRI template; this book calls it the IRI trick, and Chapter 9 shows the machinery. For now, notice that it's nothing more than an agreement about spelling.

The trick only works if the templates agree exactly. customer:{cid} in one mapping and customers:{cid} in another, or 225 in one database and 0225 in the other, gives two nodes and a federated query that silently returns nothing. Build IRIs from keys that never change (the vendor IRI uses vendor_name, so a rename would change it), and write each template once.

3.3Values carry their types

The types in c360, with SQL cousins and shorthand:

DatatypeFull formShorthandSQL cousinc360 use
xsd:string"Carolyn"quoted, no ^^varcharnames, email, state
xsd:integer"22"^^xsd:integer22integerorder quantity

xsd:date"2011-01-21"^^xsd:datenonedatepurchase date

The type decides how values sort, compare and add up. As strings, "9" sorts after "10", so "top orders by quantity" with a string quantity is wrong in a way that looks almost right. FILTER(?price > 250), the heart of the "large order" rule (Chapter 10), only works if ?price is a number; YEAR(?date) only works on a real date. And then there's arithmetic.

Where the two cents went. The order price was first mapped as xsd:float, a 32-bit binary floating-point number like SQL's real: about seven significant digits, and most decimal fractions can't be stored exactly. 439.78 as a float is really 439.7799987792969. Carolyn's true total, 502,529.42, has eight significant digits; the nearest float is 502,529.40625. Sum hundreds of slightly-off prices and the error surfaces in the cents.

The fix was one line in the Redshift mapping, casting to xsd:decimal, which is exact like SQL's numeric: BIND(xsd:decimal(?price) AS ?p). Stardog then matched SQL to the cent, $502,529.42. Rule for life: money is xsd:decimal, never float or double.

The two cents are the classic Java float-for-money bug:

RDF literals

"Carolyn"                  # xsd:string
22                         # xsd:integer
439.78                     # xsd:decimal
"2011-01-21"^^xsd:date     # xsd:date
"439.78"^^xsd:float        # never for money

Java

String     first = "Carolyn";
BigInteger qty   = BigInteger.valueOf(22);
BigDecimal price = new BigDecimal("439.78");
LocalDate  day   = LocalDate.parse("2011-01-21");
float      bad   = 439.78f;  // 439.7799987…

Where the analogy breaks: in Java the variable declares the type and the compiler enforces it. In RDF each value carries its own type and nothing enforces consistency: one price can be a decimal and the next a string. (xsd:integer is unbounded, hence BigInteger.)

When the data lives in Aurora and Redshift, a value's type comes from the mapping. The ontology can say what type a property is meant to have, but that documents rather than converts (Chapter 6). So the working mappings cast explicitly: xsd:decimal for money, xsd:integer for quantities, xsd:date for dates. Without casts, values arrive with whatever type the database driver reports.

3.4Prefixes: nicknames for namespaces

Typing <tag:stardog:api:ecomm:firstName> every time, as you did in Chapter 2, gets old fast.

TermWhat it isWhy it existsTiny example
PrefixA declared nickname for a namespace.Readability; fewer typos in long IRIs.PREFIX : <tag:stardog:api:ecomm:>
Prefixed nameNickname + local name, expanded by plain text concatenation.Short to write, identical in meaning to the full IRI.:firstName = <tag:stardog:api:ecomm:firstName>

Ours is : (also written ecomm:) = tag:stardog:api:ecomm:. The standard ones: rdf: (core terms, chiefly rdf:type), rdfs: (labels, classes; Chapter 5), owl: (richer ontology terms; Chapter 6), xsd: (datatypes) and, in the kit, so: for https://schema.org/. Full namespaces are in the Turtle file in Section 3.7.

Because expansion is pure text, one IRI can have several spellings. The kit's rules file declares stardog: as tag:stardog:api: and writes stardog:ecomm:Customer, which expands to exactly :Customer. Stardog only compares the expanded form.

Prefixes are declared per query or per file. Copy a query without its PREFIX line and it may fail with "undefined prefix". A Stardog database can also store default namespaces, so in Studio some prefixes may work when omitted. Don't rely on it: this book always declares its prefixes, so queries also run from the agent (Chapter 14).

3.5Turtle: triples in a file

Triples need a file format, the way tables have CSV and SQL dumps. The one people read and write is Turtle (.ttl), a compact text format, because one triple per line with full IRIs is correct but exhausting. The kit's ontology files are Turtle, and so is what Stardog Designer exports. Watch three facts shrink.

Full form, one triple per line, each ending in a full stop. Valid Turtle already:

<urn:stardog:demos:c360:customer:225> <tag:stardog:api:ecomm:firstName> "Carolyn" .
<urn:stardog:demos:c360:customer:225> <tag:stardog:api:ecomm:lastName>  "Inworth" .
<urn:stardog:demos:c360:customer:225> <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <tag:stardog:api:ecomm:Customer> .

With prefixes, a semicolon, and a. In a file, prefixes are declared with @prefix and a full stop. A semicolon means "same subject, next predicate". And a is short for rdf:type, the predicate that says what kind of thing something is:

@prefix : <tag:stardog:api:ecomm:> .

<urn:stardog:demos:c360:customer:225> a :Customer ;
    :firstName "Carolyn" ;
    :lastName  "Inworth" .

A comma means "same subject and predicate, another object". This line from the kit's schema.ttl is four triples:

:name so:domainIncludes :Category, :Customer, :Product, :Vendor .

That's enough to read the kit's ontology, which you'll load in Chapter 6. Its opening lines say "Industry is an OWL class labeled 'Industry'", and so on:

:Industry a owl:Class ;
    rdfs:label "Industry" .

:Customer a owl:Class ;
    rdfs:label "Customer" .

# starts a comment (like SQL's --), and whitespace doesn't matter. One trap: SPARQL declares prefixes as PREFIX, with no @ and no full stop, a frequent typo.

3.6Named graphs: folders inside the database

TermWhat it isWhy it existsTiny example
Named graphA set of triples labeled with its own IRI.To organize, secure, query and delete groups of triples as a unit.<urn:book:ch03>
Default graphThe one unnamed graph every database has.Where data goes when no graph is named.Empty in our design.
QuadA triple plus the graph it lives in.What a store with named graphs actually records.customer:225 firstName "Carolyn" in <urn:book:ch03>

The build uses these folders four ways. Organization: the ontology and the rules each get a graph, so each can be reloaded alone (Chapter 6). Cleanup: DROP GRAPH removes a whole folder. Provenance: each virtual graph has a name like <virtual://redshift_c360>, so a query can say which source it means. Security: access can be granted per graph (Chapter 12).

What does a query see? By default, a Stardog query that doesn't name a graph reads only the default graph. The database option query.all.graphs widens that to all local graphs, and special names such as <tag:stardog:api:context:all> mean "every local and virtual graph" (see Querying Stardog in the docs). This book's habit is simpler: always say which graph you mean, with GRAPH <…> { … }.

A named graph is closest to a schema in a database: c360.customer vs public.customer, a namespace you can grant on and drop. The difference: folders don't wall data off. Two named graphs that use the same IRIs connect the moment you query them together, which is how Carolyn's Aurora facts and her Redshift orders, in two virtual graphs, become one picture.

A database with named graphs behaves like a map from graph name to a set of triples:

SPARQL

INSERT DATA { GRAPH <urn:book:ch03> { … } }

SELECT * WHERE {
  GRAPH <urn:book:ch03> { ?s ?p ?o }
}

DROP GRAPH <urn:book:ch03>

Java

Map<String, Set<Triple>> db = new HashMap<>();
db.computeIfAbsent("urn:book:ch03",
    k -> new HashSet<>()).add(t);

db.get("urn:book:ch03");

db.remove("urn:book:ch03");

Where the analogy breaks: triples about the same IRI in two graphs join up automatically, which two Java sets never do. And a virtual graph isn't a stored set at all: it's closer to a lazily computed view (think Supplier<Set<Triple>> backed by SQL).

Load a file without choosing a named graph and it lands in the default graph. Then GRAPH <urn:book:ch03> finds nothing, and it's easy to believe the load failed. When a count is unexpectedly zero, first check which folder you loaded into and which you're querying.

Three parts of the blog rest on this chapter. Its mappings and IRI template section is Section 3.2. Its ontology section (built in Stardog Designer) produces Turtle like Section 3.5, stored in a model named graph. And its named-graph security section (Chapter 12) is why the virtual graphs are separate folders.

3.7Hands-on: a Turtle file in its own folder

You'll write a Turtle file about Carolyn, her address and one of her orders, load it into <urn:book:ch03>, inspect the types, and delete it. Load it from a file with Studio's Load Data dialog (Path A) or by pasting an INSERT DATA (Path B). Do one, not both.

Step 1. Create the file. Copy this block, then in Terminal run pbpaste > ~/Downloads/c360-ch03.ttl, or paste it into a plain-text editor and save as c360-ch03.ttl (in TextEdit, Format → Make Plain Text first).

@prefix :     <tag:stardog:api:ecomm:> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

# Customer 225, from Aurora c360.customer
<urn:stardog:demos:c360:customer:225>
    a :Customer ;
    :firstName  "Carolyn" ;
    :lastName   "Inworth" ;
    :email      "cinworth68@g.co" ;
    :phone      "704-619-5453" ;
    :address    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35> ;
    rdfs:label  "Carolyn Inworth" .

# Her address, from Aurora c360.address
<urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35>
    a :Address ;
    :streetAddress "78945 Thompson Plaza" ;
    :city          "Milwaukee" ;
    :state         "Wisconsin" ;
    :zipCode       "53285" .

# One of her orders, from Redshift c360.purchase
<urn:stardog:demos:c360:purchase:us:pos0e7edc35-b578-44a0-a58c-e6388bc83337>
    a :Order ;
    :purchasedBy   <urn:stardog:demos:c360:customer:225> ;
    :itemPurchased <urn:stardog:demos:c360:product:258> ;
    :quantity      22 ;
    :purchasePrice 439.78 ;
    :purchaseDate  "2011-01-21"^^xsd:date ;
    :purchaseTime  "6:53 AM" .

Count the triples first: each ; and each final . ends one, so 7 + 5 + 7 = 19. 22 and 439.78 have no quotes: shorthand for xsd:integer and xsd:decimal.

Step 2, Path A: load the file. In Studio open Databases, select kit-c360, click Load Data, and Browse to c360-ch03.ttl. In the Load RDF dialog, the Load Data To dropdown shows stardog:context:default. Don't leave it there. Click the dropdown, type urn:book:ch03 into its "Search or create…" box, and choose the option that creates it. The dropdown should now show urn:book:ch03. File Format should say Turtle. Click Load Data. Loaded into the default graph by mistake? Run MOVE DEFAULT TO <urn:book:ch03> in the Workspace to move everything across.

Step 2, Path B: paste instead. Only if you skipped Path A. In the Workspace (database kit-c360), run the same triples inside INSERT DATA, with prefixes in SPARQL form:

PREFIX :     <tag:stardog:api:ecomm:>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX xsd:  <http://www.w3.org/2001/XMLSchema#>

INSERT DATA {
  GRAPH <urn:book:ch03> {
    <urn:stardog:demos:c360:customer:225>
        a :Customer ;
        :firstName  "Carolyn" ;
        :lastName   "Inworth" ;
        :email      "cinworth68@g.co" ;
        :phone      "704-619-5453" ;
        :address    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35> ;
        rdfs:label  "Carolyn Inworth" .

    <urn:stardog:demos:c360:location:b80ea2ce-2361-408a-b443-721594cbbb35>
        a :Address ;
        :streetAddress "78945 Thompson Plaza" ;
        :city          "Milwaukee" ;
        :state         "Wisconsin" ;
        :zipCode       "53285" .

    <urn:stardog:demos:c360:purchase:us:pos0e7edc35-b578-44a0-a58c-e6388bc83337>
        a :Order ;
        :purchasedBy   <urn:stardog:demos:c360:customer:225> ;
        :itemPurchased <urn:stardog:demos:c360:product:258> ;
        :quantity      22 ;
        :purchasePrice 439.78 ;
        :purchaseDate  "2011-01-21"^^xsd:date ;
        :purchaseTime  "6:53 AM" .
  }
}

Step 3. Count the triples in the folder.

SELECT (COUNT(*) AS ?n)
WHERE { GRAPH <urn:book:ch03> { ?s ?p ?o } }

Expect n = 19. If you get 0, the data probably went to the default graph; Step 5 will show it.

Step 4. Look at the types. isLiteral keeps only plain values; DATATYPE returns each one's type:

SELECT ?p ?value (DATATYPE(?value) AS ?type)
WHERE {
  GRAPH <urn:book:ch03> {
    <urn:stardog:demos:c360:purchase:us:pos0e7edc35-b578-44a0-a58c-e6388bc83337> ?p ?value .
    FILTER(isLiteral(?value))
  }
}

Expect 4 rows: quantity 22 (xsd:integer), purchasePrice 439.78 (xsd:decimal), purchaseDate 2011-01-21 (xsd:date) and purchaseTime "6:53 AM" (xsd:string). Studio may show the types as full IRIs, such as http://www.w3.org/2001/XMLSchema#integer. The order's other three predicates point at things, so the filter dropped them.

Step 5. Which folders exist, and what does a query without GRAPH see?

SELECT ?g (COUNT(*) AS ?triples)
WHERE { GRAPH ?g { ?s ?p ?o } }
GROUP BY ?g

Expect one row: urn:book:ch03, 19. Now the default graph:

SELECT (COUNT(*) AS ?n)
WHERE { ?s ?p ?o }

Expect 0: your triples are in a named graph, and a query without GRAPH reads only the default graph. If you get 19, the database has query.all.graphs on; fine, just mention it to Claude.

Step 6. Watch the two cents disappear, computing values right in a query:

PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ("9" < "10" AS ?asText)
       (9 < 10 AS ?asNumbers)
       (xsd:float("502529.42") AS ?asFloat)
       (xsd:decimal("502529.42") AS ?asDecimal)
WHERE {}

Expect: asText = false, asNumbers = true, asFloat not quite 502529.42 (something like 502529.4, depending on how Studio displays floats), and asDecimal = 502529.42 exactly.

Step 7. Clean up.

DROP GRAPH <urn:book:ch03>

Step 8. Verify it's empty.

SELECT (COUNT(*) AS ?n)
WHERE { GRAPH <urn:book:ch03> { ?s ?p ?o } }

Expect n = 0. If Step 5 showed your triples in the default graph instead, run CLEAR DEFAULT to empty it (it's otherwise empty in kit-c360), then rerun the Step 5 default-graph count and expect 0.

You wrote a :Customer and a :Order, and Stardog accepted them even though nothing says what a Customer or an Order is. It would accept a :Unicorn just as happily. A class name is only an IRI until someone describes it in the T-Box: Chapter 4 teaches you to query properly, then Chapter 5 defines the classes.

Check yourself

Why can't RDF just use 225 as Carolyn's identifier, the way the customer table does?

A graph has no table to supply context, and 225 is also a product id in Redshift. Triples from many sources mix freely, so each name must be globally unique, as urn:stardog:demos:c360:customer:225 is.

What makes Carolyn's Aurora triples and her Redshift orders connect?

Both mappings build her IRI from cid with the identical template urn:stardog:demos:c360:customer:{cid}: same name, same node. Differ by one character and the join silently returns nothing.

What is the datatype of 439.78 unquoted in Turtle, and of "439.78" in quotes?

Unquoted, it's shorthand for xsd:decimal. Quoted with no ^^, it's an xsd:string and will sort and compare as text.

Where did the two cents go, and what brought them back?

The price was mapped as xsd:float, a 32-bit binary type that can't hold most decimal fractions exactly; summing many prices accumulated the error. Casting to xsd:decimal in the mapping made the total match SQL: $502,529.42.

Write in compact Turtle: customer 225 is a Customer, first name "Carolyn", last name "Inworth".

<urn:stardog:demos:c360:customer:225> a :Customer ; :firstName "Carolyn" ; :lastName "Inworth" . with @prefix : <tag:stardog:api:ecomm:> . declared. a means rdf:type; ; repeats the subject.

You loaded a file and GRAPH <urn:book:ch03> finds nothing. Likely cause?

It was loaded without a named graph, so its triples went into the default graph.

Chapter recap

  • IRIs are globally unique names, compared as exact strings: urn:stardog:demos:c360:… for data, tag:stardog:api:ecomm:… for vocabulary.
  • Data IRIs are built from keys by templates; Aurora and Redshift both use …customer:{cid}: the IRI trick.
  • Every literal carries its datatype, which decides sorting, comparison and arithmetic. Money is xsd:decimal; float cost us two cents.
  • Prefixes are text abbreviations; : is tag:stardog:api:ecomm:.
  • Turtle is the readable file format: @prefix, ; for same subject, , for same predicate, a for rdf:type.
  • A database has one default graph and many named graphs. Always name the graph you mean; unnamed loads land in the default graph.
